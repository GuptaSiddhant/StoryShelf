# Changelog

All notable changes to StoryShelf. Every published package shares one version. Entries are written as
changesets (`.changeset/*.md`) in the pull request that makes the change and are rendered here when a
release is prepared (`scripts/version-packages.mjs`, ADR 0043); do not edit this file by hand.

## 0.10.0 (2026-11-09)

API change: every `/api/v1` error now answers JSON, `{ "error": { "message": string } }`, with the same status as before, as the OpenAPI document always declared. Until now most refusals (unknown project or build, forbidden, validation failures, upload limits, duplicate keys) answered plain text, and a few guards answered `{ "error": string }` or `{ "message": string }`, so generated clients read the body the wrong way. One handler now answers the refusals, an unexpected error (a generic `Internal Server Error`; the detail is logged, never sent) and unknown API paths (JSON `404`), and a request that fails validation answers `400` with the failed fields in `error.message` (it used to send the serialized Zod error, `{ "success": false, "error": { "issues": … } }`, which exposed the validation library's internals). The `baseline_changed` `409` keeps its `code`, `snapshotId` and `baselineStatus`, now inside `error`; the setup gate's `failures` too. The OpenAPI document declares one shared `Error` schema on every error response. Pages, forms and the requests the app's own pages make with HTMX keep the answers they had. The `storyshelf` CLI reads `error.message` and falls back to the raw text for an older server, so it prints the same messages against both. The readiness probe `POST /api/v1/health` is the one exception: it still answers its report (`status`, `adapters`), with `503` when degraded. **If you parse error text by hand**, read `error.message` from the JSON body instead.

Added: reviewers assigned from component ownership (#465, #437). A project admin can map story-file globs to project members on the Members tab (**Component owners**, one CODEOWNERS-style rule per line, a glob then member ids; an id that is not a member is refused and nothing is saved). When a build waits for review, the owners of the components it added or changed are its **assigned reviewers**: each gets one `review:requested` that says why ("You were asked to review this because you own ..."), even if they turned the default email off, and the build page lists them with where they stand. Assignment is advisory: approvals, verdict rules and statuses do not change, and any approver can still approve. With no matching owner, the default approvers are asked as before. `projects` gains a `component_owners` column on all three databases (added to existing ones on start).

Changed: shared Storybook content is now tracked as per-build uses instead of a counter. A new `content_uses` table holds one row per (build, hash), written idempotently by both upload paths (`persistStorybookStatics` and the file-by-file manifest route) through `BuildReferenceLifecycle.recordContentUses`; a build that uses one hash at several paths has one row. The unused `content_refs` table, which never held rows on a real adapter, is dropped on startup (`db.tables.contentRefs` and `ContentRefModel` are replaced by `db.tables.contentUses`), and its error-swallowing counters are removed. Content collection claims a blob in the capability's concurrency domain (`claimContent` under a per-pass token, `holdsContentClaim`, `abandonContentClaim`, `finishContentCollection`), so a use racing a delete ends in exactly one outcome: the manifest route answers 409 and the publish job retries when a blob was claimed first. Custom adapters that implement `BuildReferenceLifecycle` must add the five new methods. File-backed SQLite exposes the capability (#536), so content uses are recorded and collected there; other databases record and collect nothing.

Review-request notifications are retried: on a long-running host each recipient of a build's review request is a `review-request` job on the notify queue, re-resolved when it runs and retried alone if the delivery is refused.

Added: git channels show when they last delivered, and project admins can retry a channel's current state. Notification channels record `last_delivered_at` (set on a successful delivery, left alone by a failure) and the API and settings page show it next to the sanitized latest error. A new **Retry current state** action (`POST /api/v1/projects/{slug}/notification-channels/{channelId}/retry`) asks again for the open builds of the project on that one git channel, never replaying chat, email or webhooks; it needs a project admin and a confirmed public URL.

Add `testing.maxJobSeconds` (default 7200): a wall-clock bound for every job. Past it the job's lease is no longer renewed, its work is aborted through the `AbortSignal` its handler receives, and the normal retry or exhausted path takes over, so a hung job can no longer hold a slot forever. A capture that hits the bound ends its build `failed` and records `job deadline exceeded (<n>s)` in its attempt log.

Build retention is now active on Postgres through the default `postgres.js` preset (`createPostgresDatabase`). At boot the adapter prepares the baseline pins, then exposes the build-reference lifecycle, so with `testing` enabled the build purge and branch GC run and keep any build a baseline still needs. A baseline whose recorded source build is being deleted or belongs to another project pauses retention and is named on the System page; fix it and restart. Upgrade every server instance that shares the database before relying on it. PGlite, `./neon`, `pg` and `./neon-http` still keep builds (fail closed).

Added: `storyshelf protect --provider github` understands repository rulesets. When a ruleset applies to the branch, it confirms the required StoryShelf check there, and with `--apply` adds it to the repository ruleset that already has a status-check rule or creates a "StoryShelf merge gate" ruleset; with no ruleset it uses classic branch protection as before. The output says which mechanism it used, including on a dry run. GitLab is unchanged.

Added: `@`-mention project members in review comments (#463, #437). A comment can name a project member with `@alex.doe` (the part of their email before the `@`) or `@Alex Doe` (their display name). The server resolves it against that project's members only and stores the ids in a new nullable `comments.mentions` column (JSON, in SQLite, Postgres and MySQL; existing databases get it on start-up). A handle that names no member, or two, stays plain text. Mentions show highlighted with the member's current name, and the API's comments carry `mentions: [{ userId, handle }]` (never read from the request). Each mentioned member gets one `comment:mentioned` notification: by email by default, through their subscription's channels when they have an enabled one, never to a project channel or a webhook, and a member who is subscribed to `comment:created` and mentioned gets the mention instead of the comment. The comment box suggests members as you type `@` (two new `review` page routes, `mention-suggest` and `mention-complete`).

Changed: every comment raises one `comment:created`; `review:comment` is a filter alias (#448, #271). Build and story comments used to raise `review:comment` and only snapshot comments `comment:created`. Now every comment raises exactly one `comment:created`, whose payload has `scope` (`build`, `story` or `snapshot`) and `eventId` (the comment id, repeated by a retried delivery so receivers can de-duplicate). A notification channel or subscription that lists `review:comment` still receives build and story comments (not snapshot comments), and one that lists both names receives one message. Webhooks now also receive snapshot comments, and send `X-StoryShelf-Event: comment:created`. A webhook whose `events` lists `review:comment` keeps receiving build and story comments: one shared predicate in core (`matchesEvent`) applies the alias to webhooks, channels and subscriptions.

Fixed: one `review:requested` per review cycle (#449, #271). A repeated publish completion or a retried hook used to send another review request. A build now has a review cycle (`builds.review_cycle`, default 0, incremented when a build goes back to `pending` from `approved` or `rejected`), and the request is claimed once per cycle with an atomic write (`builds.review_requested_cycle`), so a repeat or a second instance sends nothing while a genuinely reopened build sends a new request. The event carries `data.eventId` (`<buildId>:<cycle>`). Both columns are added to existing SQLite, Postgres and MySQL databases on start (defaults 0 and null).

Added: the component page can show one build, `?build=<id>` (#451, #271). The page used to show only the newest build that has the file. With `?build=` it shows that build's states, stories, results and story comments, with a banner (and a **Show latest** link) when it is not the newest; tabs and links keep the parameter, and History rows pick a build. A build that is not the project's, or does not exist, answers 404 and never falls back to the newest build; a valid build without the file says so and shows no states. Links from build and review pages pass their build. Without the parameter nothing changes.

Added: change requests on review comments (#464, #437). A comment can now be marked a change request (`kind: "change_request"` on `POST …/comments`, or **Request a change** in the forms). Developers, approvers, admins and the build's author resolve and reopen it (`POST …/comments/:commentId/resolve` and `…/reopen`; a viewer gets 403); `comments` gains `kind`, `resolved_at` and `resolved_by` on all three databases. The build page shows the count of open change requests beside the verdict and a checklist linking to each anchor, and **Approve build** asks for confirmation while some are open. They are advice only: they never block approval or change a status. `comment:created` carries the `kind`.

Added: a resumable build-deletion driver for databases with the build lifecycle capability. A claimed build is finished in three recorded steps (release shared content, delete storage, remove rows), so a crash resumes at the first unfinished step and shared content is released exactly once per build. Purge uses it when the capability is present, and content collection now also keeps any blob a live build's manifest names. `BuildReferenceLifecycle` gains `listDeleting`, `releaseBuildContent`, `markStorageDeleted` and `completeDeletion` (custom adapters that implement the capability must add them). SQLite gains the `build_deletions` and `build_content_releases` tables. File-backed SQLite exposes the capability (#536), so its purge uses this driver.

Added: turn review-request emails off per project (#450, #437). A project member can switch `review:requested` off with **Send me review requests** (`reviewRequests` on `PUT …/notifications/me`, default `true`) without touching their other topics or channels; `notification_subscriptions` gains `review_requests` on all three databases, and existing rows keep receiving it. Unticking **Email me**, here or on the profile page, now keeps the subscription switched off instead of deleting it, so it no longer falls back to the default recipients. The topic checkboxes come from one list in core (`NOTIFICATION_EVENTS`), so `review:verdict`, `design:changed` and `insight:ready` appear (`review:requested` has no checkbox: the switch is its only control), and ticking every box stores all topics (`events` null) so later events still arrive.

Added: build retention now works on SQLite deployments with `testing`. When the schema is migrated at boot, the SQLite adapter prepares the baseline pins once and then exposes the `buildReferenceLifecycle` capability, so `POST /api/v1/admin/purge` and the daily branch GC run in a testing deployment (a baseline's source build is never purged) instead of answering `503`. The purge response gains `protected` (builds a baseline still needs) and `resumed` (builds an earlier interrupted run had claimed). If a baseline's recorded source build is being deleted or belongs to another project, retention stays off, the server logs the baseline and build ids once, and the System page shows "Retention is paused" until the data is fixed and the server restarted. The daily retention timer can now purge builds too, but only when `config.purgeTtlDays` is set explicitly (there is no default, so an upgrade never starts deleting builds): it runs only the capability's deletion path and does nothing without it. The built-in servers map `PURGE_TTL_DAYS` to it; the Fly demo sets 14. In-memory SQLite and Postgres/MySQL keep refusing to purge with `testing`. `DatabaseAdapter` gains the optional `retentionPause`, which the observability wrapper forwards.

Security fix: the sign-in gate let an anonymous request through to any project page whose path contained `/storybook` (a component import path with `storybook/` in it, a component named `storybook`, a label value like it). It now skips the gate only for the published-Storybook routes, `/projects/<slug>/storybook` and below; every other project page redirects to the sign-in page as before.

Fixed: preparing baseline references no longer clears a baseline's recorded source build when the build row is gone (the source stays recorded and is counted as unavailable), and it now stops with a typed `BaselineSourceIntegrityError`, rolling everything back, when the source build is being deleted or belongs to another project. File-backed SQLite runs this preparation at boot before it exposes retention; the other dialects do not run it.

A design render fetched with a member's own connection is now served `Cache-Control: private, no-store`, so a browser no longer keeps it after the member signs out. Project-wide renders keep their caching.

Affected capture no longer inherits a baseline that a later build promoted (for example by a per-snapshot approval while that build was still in review): the story is rendered again, so reverting it to the comparison build's version is not hidden.

A remote browser that disconnects in the middle of a pass now ends the pass with one `RemoteBrowserLostError` (no more stories are scheduled on it and none after the drop is recorded as a story failure), the lease is released as failed, and the job is retried through the queue; a page crash and a cancel are unchanged.

Count the snapshots a shard captures again after a redelivery as the `storyshelf.capture.shard.repeated_snapshots` OpenTelemetry counter; it is a no-op without an SDK.

A cancelled build now shows no verdict controls on its review card, the same as a failed one (a cancelled build is terminal). The capture progress bar sets its fill width through a class instead of an inline style, and the UI consistency check now also scans `src/ui/` for inline styles.

Fix: two overlapping enqueues of one build could both stamp it and leave a superseded capture job running. A build's capture job now claims the build before it is queued, in one conditional write that also advances the run generation, so only one of two concurrent enqueues claims it. The job carries that generation and its worker ends it `cancelled`, writing nothing, when a retry has started a newer run. Finalizing a build (its final status and the dropping of orphan baselines) is conditional on the run's generation too.

Fixed: a capture enqueue that was slow to record its job could overwrite the run of a retry that completed meanwhile, leaving the retried build capturing. Builds now carry a run generation (`builds.capture_generation`, added by migration with default 0): a retry advances it, and an enqueue records its job only while the generation it read is current, otherwise its job is cancelled.

Fixed: a trailing slash in the server url no longer breaks every request. The url is normalized once (a path prefix is kept), and a server that answers with an HTML page instead of JSON now gets a plain error that names the origin and suggests checking the url.

Review: the screenshot panes of the comparison (baseline, current, diff) can be scrolled with the keyboard. A pane that shows an image takes focus, has a name and a visible focus ring, and the arrow keys pan it when it is zoomed in or the screenshot is tall; `j` and `k` still step between snapshots. (#598)

Content collection now reads the live builds' manifests eight at a time instead of one after another, which makes a pass on a remote store (S3, GCS, Azure) about eight times faster; a candidate is still kept when any live manifest names it, and the scan still stops once none is left. A manifest that cannot be read, or that is not a valid manifest (not a JSON object), now ends the pass without deleting anything: every claim is given back and one warning with the counts is logged, where before the error stopped the pass and left the claims to expire.

Added: on a file-backed SQLite database, the first boot after the upgrade records the content uses of builds published before `content_uses` existed, from their manifests, so their shared blobs can be collected once those builds are deleted. It runs in the background, keeps its progress, deletes nothing and skips any manifest value that is not a content hash.

Fixed: when a crashed shard's hook ran again after an earlier pass had already finalized the build but failed before closing its capture attempt, the retry returned "skipped" and left the attempt open forever. It now closes the plan's attempt (with the story and failed counts rebuilt from the plan and shards, without finalizing the build again) and reports "finalized"; a hook that arrives after a retry replaced the plan leaves the newer run's attempt alone.

The Delivery cell of a failing notification channel shows the failure time and its error on separate lines, so "Failed 5 h ago" no longer breaks mid-phrase and a long error truncates with an ellipsis instead of running past the cell.

Fixed: links to a component whose import path has a `.` or `..` segment (such as `../ui/Button.stories.tsx`) and to a label value with one now open the right page. A browser resolves such a segment before the request, so `UrlBuilder` gives these values the query form of the same page (`?path=` for components, `?value=` for labels), which the pages accept next to the path form. All other links keep their form.

Notifications to a person are checked against their project access when they are delivered: a removed member's subscription stays but sends nothing, while site admins and viewers keep theirs.

Fixed: an inline Storybook zip that is invalid or breaks an extraction cap now ends its build `failed` (with `build:failed` carrying the validation message), instead of leaving it `pending` forever. A git check already queued for the build resolves to a failure, and a later upload to that build answers `409`; run `storyshelf upload` again to create a new build. The CLI's `422` hint no longer offers to reuse the build.

A remote browser failure thrown as something other than an `Error` (a WebSocket error event, a plain object, a string) now keeps what it says instead of `[object Object]`, with its cause chain, secrets removed; a transient outage thrown as an event object is retried instead of marking the target unavailable. `Error` instances classify exactly as before.

Fixed: a personal notification subscription no longer silently loses messages to a room kind (#538, #437). A subscription is personal, so `via` may only name kinds that address one person; notifier providers now declare `audience` (`person` for email, `room` for Slack, Teams and the log notifier). Saving a subscription that lists a room kind such as `slack-webhook` answers 422 and points to project channels. An existing row that lists one keeps delivering over its personal kinds (mentions, review requests and every other topic share the rule), skips the room kind and logs one warning per subscription and kind, with no addresses.

Fixed: the health report no longer says `ok` when an adapter it does not probe failed its boot check (#544). `POST /api/v1/health` and the admin System page used to list only the adapters they probe (database, storage, capture runner, design, notifiers, email), so a failed AI, auth or images setup left the status at `ok`. Such a failure now appears as its own `failed` entry with its category, kind and a sanitized detail, and the overall status becomes `degraded`. The response shape is unchanged, and a successful setup adds nothing. The shared secret redactor now also hides Anthropic API keys (`sk-ant-…`) in adapter errors, health details and logs.

Fixed: a build reviewed or accepted without its published Storybook no longer shows a permanent pending `storybook` check (#445, #265). A build past capture (`reviewing`, `approved` or `rejected`) with no manifest and no open `publish` job now shows the `storybook` status as `failure` with `Storybook content unavailable, see build page` (neutral on GitHub check runs, since it is informational); while a publish job is queued, running or exhausting it stays pending, because with `testing` on a capture can finish before publishing does. The build's review card says to re-upload the build or purge it, and a verdict is refused with that text. The queue gains an `onEnded` hook, called after a job reached `done` or `failed`, and the publish job uses it (and tells the build when it is abandoned) so the git state is refreshed once the job has really ended. A capture that failed after a successful publish still shows the capture failure with a published Storybook.

Reusing pages (opt-in) now also deletes every Cache Storage entry and unregisters service workers of the Storybook origin when a page is reset between captures, so one story cannot affect the next through them.

Accessibility: an inherited snapshot shows its baseline's findings behind a `from baseline <sha>` note, kept out of the build's own totals; a `Date`, `Set` or `Map` in `parameters.a11y` is read as an ISO string or an array, and a cyclic or too deeply nested parameter runs axe with its defaults and stores `a11y parameters not serializable: <reason>` as a note instead of looking like no parameter.

Forked capture now forwards a shard run's repeated-work event from the worker child to the parent over IPC (a new `shard-repeated` message carrying counts only; a parent that does not know it ignores it), so the parent can count it.

Changed: a caller with no role on a project, signed in or not, now gets `404 Project not found` from its API routes, pages and the published Storybook of a private build (including the `/_/:id` short links; public builds stay readable without sign-in), the same answer as for a project that does not exist, instead of `403`, the page itself or a redirect to sign-in. `403` remains for a member whose role is too low for the action. Browsers now get a not-found page instead of a line of text; for a visitor who is not signed in it has a **Sign in** link, and the sign-in page honours a same-site `return_to` path (password, OAuth, SSO and passkey sign-in) so they land back on the page they were opening.

Over https the CSRF token is bound to the signed-in session again, and the profile page marks the current device again: the app read the session cookie as `storyshelf_session` only, but the auth engine names it `__Secure-storyshelf_session` on https. One `readSessionCookie` helper in `@storyshelf/core/types` prefers the `__Secure-` name and falls back to the plain one.

The CSRF token no longer carries the session cookie's value (it was `<session>:<time>:<signature>` and is rendered into pages, so a script could read the HttpOnly cookie from it); it is now `csrf:<time>:<signature>`, and tokens issued before still verify.

Fixed: GitHub check runs are idempotent and follow changed findings. A check run is found among all runs of the commit with its id, and when two deliveries race to create it the runs are listed again and every run with the id is brought to the same state. Annotations are compared finding by finding (and by the hash of the set in the run's summary) instead of by count, so a changed finding is posted even when the count is unchanged and a repeat adds nothing. The summary lists the current findings first and says how many earlier annotations on the run are history.

The design render route (`GET /api/v1/projects/:slug/design/renders/:renderId`) is now a hosting route: component design links render on an instance without `testing`, so it no longer answers 404 there.

The review-schema check, which names the table and column of a build_reviews table or review column made outside StoryShelf, now also runs when better-sqlite3, bun:sqlite, D1 and Turso start, through one small table-info reader that works for sync and async clients.

Security hardening: the error of a failed remote `connect` keeps only redacted provider text (URLs cut to their origin, Bearer/Basic header values and known secret shapes redacted, at most 300 characters) and no longer carries the thrown value as its cause.

The package manifest no longer declares a `types` file (`dist/index.d.mts`) that the build never emitted.

Affected capture renders a story at every viewport when only one viewport's baseline was promoted after the comparison build, instead of also inheriting its other viewports, which wrote the same snapshot twice.

Two label-type refusals no longer answer a server error. A create that loses a race for the same key (two requests at once; the unique index turns the second away) now answers `409` with "A label type with the key '…' already exists", like the sequential duplicate, instead of `500`. Deleting a reserved label type through `DELETE /api/v1/projects/{slug}/label-types/{key}` now answers `400` with "Label type '…' cannot be removed", instead of `500`. Both responses are declared in the OpenAPI document.

An upgrade that meets a build_reviews table or a review column made outside StoryShelf (a missing column, or a type that cannot hold the setting) now stops with an error naming the table and column, instead of a raw driver error or a silent skip. On SQLite this covers the `node:sqlite`, `better-sqlite3`, `bun:sqlite`, D1 and Turso drivers when table metadata is available; a D1 binding that refuses `PRAGMA` keeps its previous behavior.

The changeset card on the build page now says a changed component has different story-index metadata and that changes to args or source alone do not show, instead of implying the story definition changed.

The @mention suggestions under a comment box now look like choices: each has a border at rest, a hover and press background, and one highlighted state shared by the selected option and keyboard focus. They are built on a new `OptionList` and `Option` facade.

Fixed: a build cancelled while its stories were rendering can no longer move baselines. A capture-path baseline promotion is now refused when its build is `cancelled` or a retry has moved it to another capture generation (checked in the same transaction as the write where the database supports the reference lifecycle, right before it elsewhere), and finalize no longer drops the baselines of stories a cancelled run did not reach. Snapshots already written stay as diagnostic data.

Security fix: a database, storage or library failure inside a settings form, the project or label API, the public-origin form or the invite page no longer sends its internal text (driver messages, SQL fragments, file paths) to the browser or API client. Those handlers now answer with their generic text ("Failed to update", "Failed to create project", "Invalid origin", and so on) and log the original error. Refusals written for the user still reach them unchanged: a duplicate or reserved label type, an invalid public origin, an invalid capture target, the password policy and an invalid or expired invite. Core exports `UserFacingError` for code that refuses on purpose. Authors of an `Auth` adapter outside this repository: throw `UserFacingError` from `acceptInvite` for any refusal you want shown on the invite page (an invalid or expired invite, a password policy); a plain `Error` now reads "Invalid or expired invite" there. Adding a label type with a key the project already has is now refused with a clear message instead of a unique-index error.

A build that failed or was cancelled now says "Nothing to review: this build failed." (or "was cancelled.") on its review card instead of an approval counter and rejection text, with a Retry capture button for people who may retry (when capture is on). A cancelled build now shows that card on its page too.

UI: the settings tabs no longer scroll sideways on a phone. A card holding a wide table (the notification channels) grew past the viewport, so the page scrolled by up to 470px at 375px; the table now scrolls inside its own region. (#561)

Fixed: wiring two notifiers that declare the same `metadata.kind` now fails at boot with an error naming both providers (`kind "log" is already used by "…"`), because a stored channel names its provider by kind and the second provider would answer for the first one's channels. Distinct kinds, as in the shipped chat, email and git providers, are unaffected.

Fixed: when an admin replaces the confirmed public origin with a different one, the state of open builds is requested again, so git statuses already posted stop linking to the old origin. Before, only the first confirmed origin did. Saving the same origin again, or a detected-but-unconfirmed report, asks for nothing, and chat, email and alerts are still never replayed.

Groundwork for build retention on Postgres: the build-reference lifecycle (fenced reference replacement, deletion claims, content uses and claims) now exists for postgres.js and PGlite, with row locks taken in a fixed order, and passes the shared contract suite on both PGlite and a real server. No preset exposes it yet, so Postgres deployments with `testing` still skip automatic build deletion until a following release switches it on.

The Postgres schema now has the build retention tables (`build_references`, `build_reference_generations`, `build_deletions`, `build_content_releases`) and `builds.retention_state`, created on a fresh database and added on upgrade. Nothing reads them yet; Postgres still reports no retention capability.

Added: a signed story preview now says, under the preview, that it reloads itself every 40 minutes to stay signed in (from the configured interval). When a renewal still fails after its retries, a warning notice replaces that line with a "Reload preview" button that asks for a fresh signed link now, announces itself politely, and moves focus into the frame on success. The sandbox is unchanged. `Alert` takes an optional `role` (`"status"` for a polite message).

Fixed: the AI per-project call limit now holds under concurrent requests (#545). A run reserves one of the project's calls before the model is called (a pending usage row with no tokens, counted as a call; a reservation that never gets a provider answer stays a failed call with zero tokens), so N parallel insight requests can no longer all pass the check and overshoot `perProjectCallsPerHour`. `AiUsageModel` gains `reserve`, `attach`, `complete`, `settleFailed` and `release`. Usage totals for sequential calls are unchanged. The daily token cap can still be overshot by the output of the calls already running.

The upgrade check now also refuses a hand-made `projects.run_a11y` or `snapshots.a11y_violations` column of another type, naming the table and column; the MCP `get_project` tool describes the `runA11y` setting it returns; the docs say that upgrading turns accessibility checks on for existing projects.

The comment tools now say "review is off for this project" when the project has review off, instead of "not found: check the project slug and build id". A wrong build id still reads as not found.

A build purge now reads the retention lifecycle capability once, when a pass starts, and uses that same capability for every deletion of the pass. A capability that is cleared while the candidates are being selected can no longer turn a manual or scheduled purge into an unfenced one.

A shard that runs again after an earlier attempt had stored snapshots now says so: one attempt-log line on the build (`re-captured N snapshots an earlier attempt of shard S had already stored (attempt A of L)`), a structured log line, and a `shardRepeated` metrics hook on the consumer. Nothing is resumed or skipped; the earlier rows are still replaced.

Affected capture now compares against the newest earlier build on the branch that was approved, instead of any earlier build: a build still in review, or cancelled, failed or rejected, no longer hides its changes from the next build. With no approved build the capture is full.

The builds page names its reuse metric "Average inherited share per build" and says what it measures (the last N builds, capture reuse and not time or cost saved); the docs describe it and the order of `delay` and `play` when capturing.

Fix: a capture job that waited for a forked child's slot, or was pushed to it again after a crash, is checked once more inside the capture handler right before it runs, so a run superseded by a retry in the meantime writes nothing.

Fixed: an upload that shares a blob with a crashed collection pass no longer fails with a retry error until the next purge. Recording a build's use of shared content now clears a claim older than the collection lease and goes ahead; the stalled collector then finds it no longer holds the claim and deletes nothing. A claim still inside its lease keeps refusing.

Fixed: recording a build's use of shared content now refuses a build that is gone or being deleted, so a publish that races a deletion can no longer pin shared blobs for good.

Fixed: on a signed preview, an automatic renewal that was still in flight when someone pressed **Reload preview** no longer overwrites the reloaded frame or brings the failure notice back when it settles late.

Adapter authors can run the retention activation contract suite (`retentionActivationContractSuite` in `@storyshelf/core/test-helpers`) against a dialect's baseline preparation, and the build reference lifecycle suite now covers invalid generations, racing updates and multi-owner rollback.

Security hardening: the retention paths that record a build's use of shared content and collect unused content now build their `content/…` keys with the validating `contentKey` helper. A stored value that is not a 64-digit lowercase hex digest is never recorded as a use, never looked up in storage and never deleted; it is skipped, counted, and logged once without its value.

Fixed: retrying a git channel's current state now says so when the open builds could not be looked up ("Couldn't look up open builds, try again", HTTP 503) instead of reporting that there was nothing to retry. The boot replay and origin-change replay keep their never-rejects behaviour.

Changed: a retry of one project's git channel now reads that project directly instead of listing every project and filtering. Nothing a caller sees changes.

Changed: the build-reference lifecycle contract no longer has the unfenced `replaceReferences` and `replaceManyReferences`; only the generation-fenced `replaceFencedReferences` and `replaceManyFencedReferences` remain, so no write can bypass the fence. Nothing in StoryShelf called the removed methods; a custom database adapter that implements `buildReferenceLifecycle` must drop them (breaking for such adapters; file-backed SQLite is the one built-in adapter that exposes the capability). The shared contract suite now also covers stale multi-owner rollback, release keeping the generation, admission to a deleting or missing build, and opposite-order admission.

A database adapter can now declare `metadata.transactions: "sequential"` when its `transact` cannot roll back. The Neon HTTP adapter does, so the queue no longer treats its emulated transaction as atomic when it ends a single-flight job and hands over its key (it takes the ordered two-step path), and booting with `testing` on such a database logs a warning.

Security hardening: the session cookie's attributes are now set explicitly (`HttpOnly`, `SameSite=Lax`, `Path=/`, and `Secure` when the public URL is https) instead of relying on Better Auth's defaults, and a test signs in over http and https and checks the `Set-Cookie` line, so a library upgrade cannot loosen them. `SameSite=Lax` is what keeps a cross-site form post from sending the session to a cookie-authenticated write. There is no change for existing sessions: the values are the ones the library already used.

A short link (`/_/<build id or project slug>/`) to a public build now opens for a visitor who is not signed in, instead of sending them to the sign-in page first (ADR 0011). A private build and an id that does not exist both answer with the sign-in redirect, so a short link never confirms that a private id exists.

Wait for the Storybook preview to finish starting before reading story parameters, so a remote page no longer fails with `SB_PREVIEW_API_0005` or silently loses its parameters.

Fixed: when a request for a single-flight key (a git-state notification, for example) arrived while its job ran, the job's end and the successor that serves that request are now one transaction. A crash can no longer end the job and lose the request; a database without transactions keeps the old two-step end. A request that arrives while a job's lease is exhausted is also served by a successor now, instead of failing to enqueue.

A unique index that existing rows already violate no longer goes unnoticed. The design-link index is still left out so an upgrade boots, but the database now logs one `error` with the table, the index, the number of repeated keys and how to fix it (never a row), and tries to create the index again on every boot. MySQL now skips that one duplicate-entry error for this index too, instead of failing the boot.

Fix: on the built-in SQLite adapters (`node:sqlite`, better-sqlite3, `bun:sqlite`), a plain statement issued while a transaction was awaiting ran inside that transaction, so a rollback silently undid an unrelated write. Plain statements now wait their turn behind an open transaction, and a plain call on the outer adapter from inside a `transact` callback fails at once with a message to use `tx`.

Fixed: overlapping `transact` calls on the SQLite adapters (node:sqlite, better-sqlite3, bun, D1, Turso) no longer fail with "cannot start a transaction within a transaction". The adapter runs one transaction at a time and queues the rest, so approvals and the queue's acknowledgements under load commit instead of erroring. Where the runtime has async context tracking (Node, Bun) a transaction that opens another on the same database fails at once; elsewhere, such as a Cloudflare Worker, a transaction that has waited 30 seconds for its turn fails with an error, which ends the transaction it sat in and frees the queue.

Fixed: in GitHub `checks` mode, a late delivery for an older build no longer overwrites the check run of a newer build of the same commit. The run's link names its build; build ids sort by time, so when a run of the commit already links to a newer build the older delivery writes nothing. A link whose build cannot be read is updated as before.

Stop a job's work at its deadline instead of letting it keep writing next to its redelivery. After `testing.maxJobSeconds` an abandoned capture stops at its next attempt-log line or progress report and posts no snapshot, status or build state; publishing stops before each file it extracts or persists and leaves the shared scratch directory to the redelivery; a notify delivery writes no git status and records no outcome once its attempt expired.

Fixed: a migration statement that fails now stops the boot. The Postgres and SQLite adapters used to swallow every error from their follow-up ALTERs, index changes and DDL, so a lock timeout or a permission error let boot carry on with a column missing and fail later at run time. Now only the error that says a statement is already done is skipped: a column added by another boot, a column already dropped, and a unique index over rows that already repeat its key (the index is then not built). On SQLite, a `comments` table that still requires a user is now rebuilt for real: the rebuild had never run on node:sqlite (a row read as an object where the connection returns arrays) and copied too few columns everywhere else, and both failures were hidden. It now copies every current column and swaps the table in one transaction.

Fixed: a single-flight job that failed with a request waiting could start its successor twice when two instances settled it (an exhausted job whose hook run was taken over). The marker that records the waiting request is now cleared by one conditional write, and only the settler whose write cleared it starts the successor.

UI: the scrolling `Table` surface is a keyboard-focusable, labelled region with a visible focus ring, so a wide table can be scrolled without a mouse. (#559)

UI: every table is a focusable region with its own accessible name ("API tokens", "Members", "Webhooks" and so on), so a keyboard user can scroll a wide table and a screen reader announces which table it is. A table without a name is no longer a landmark, which fixes pages with two tables both announced as "Table". (#571)

UI: `TextareaField` takes a `monospace` option for fields that hold patterns or code. (#558)

Security fix: content hashes sent to the file-by-file upload routes (`dedup`, `manifest`, `content`) are now checked to be 64 lowercase hex digits before they are used. Before, any string became part of the storage key `content/<hash>`, so with the local storage adapter a hash such as `../<other project>/…` could overwrite files of another project and the dedup route could be used to probe for them. A malformed hash now answers `400` before any storage call, the uploaded bytes must hash to the name they are stored under, and the upload, statics, catalog-reading and published-compression paths build their `content/…` keys with one validating `contentKey` helper. Nothing changes for the CLI, which already sends SHA-256 hex digests.

UI: a stack no longer grows wider than the screen. A vertical stack's single column was as wide as its widest child, so the Builds list, the Library component history and the empty Projects page scrolled sideways on a phone (by up to 460px at 375px); the column now fits the page and a wide table scrolls inside its own region. A code snippet that scrolls sideways now takes keyboard focus, so a keyboard can scroll it. (#584)

It is not part of `infraHash`, so no baseline changes identity and nothing migrates; a fingerprint without it is version 1. When a later release changes a probe, the components it re-measures are compared as unknown across versions instead of as a mismatch, and the review shows "Environment partly unknown (measurement updated)". Nothing changes yet: version 1 is the only version.

**Added: unstable render detection.** A snapshot that differs from its baseline is now rendered
once more in the same pass; when the two renders differ from each other it is flagged **Unstable
render: likely flaky** in review, with a pointer to ignore regions and `flakyTest`. The snapshot
stays a change to review and the build and git status are unchanged. New project setting **Detect

ids like `./src/ui/kbd.tsx` and never found, so every story was inherited and nothing was

## 0.8.0 — Remote browser leases, ignore regions, redaction and retention safety (2026-11-03)

**Added: ignore regions (#456).** Elements matched by `parameters.storyshelf.ignoreSelectors` (or `parameters.chromatic.ignoreSelectors`), `[data-storyshelf-ignore]`, `.chromatic-ignore` or `[data-chromatic="ignore"]` are hidden before the screenshot, keeping the layout, so dynamic content such as timestamps no longer produces a diff. Both runners apply the same mask; a selector the browser rejects is skipped with a warning and never fails the capture. Adding a mask to a story produces one expected diff the first time.

**Added: compare a snapshot to its Figma design in review (#457).** When a snapshot's component has a cached Figma render, the review stage offers a **Compare against: Baseline | Design** switch. The Design view shows the screenshot beside or over the render with side by side, swipe and onion skin. It is a visual reference only: no pixel diff or score, and it never changes a status, verdict or git state.

**Added: an optional per-process cap on remote browser connections, `maxConnections` (#467, #273).** A remote service can now limit how many connections the process holds to it at once, separately from the page limits (`sessions`, `maxPagesPerConnection`). A slot is taken before `connect` runs and returned with the lease, once, on finish, failure, cancel and shutdown; a connection shared by several pages counts once. Renders over the cap wait, a cancel or shutdown ends the wait, and a wait longer than `timeouts.acquireMs` is logged once with the target and the limit. Available on `defineRemote`, `remote()`, `playwrightServer()` and `cdp()`; unset behaves as before. It is per process, not deployment-wide.

**Changed: with `testing` on, automatic build purge and branch cleanup stop unless the database proves it can do them safely (#354, ADR 0039).** Purging a build could race a baseline promotion and delete a build a baseline had just started to reference. Until the database adapter offers the build-reference lifecycle capability (SQLite first, then Postgres and MySQL), deployments with `testing` skip automatic build deletion and branch cleanup, and `POST /api/v1/admin/purge` answers 503 with an explanation. Storage therefore grows on those deployments until the capability ships; hosting-only deployments purge as before. Comparisons keep a frozen copy of the reference image, so older diffs stay reviewable.

**Fixed: disabling a user is saved on Postgres and MySQL (#418).** The `users` table on those backends lacked `disabled`, `auth_provider`, `password_hash` and `display_name_override`, so a disabled user stayed active there. The columns are added on start-up to existing databases.

**Fixed: outbound HTTP logs and spans no longer contain secret-bearing URLs (#408), and webhook delivery reports HTTP failures (#409).** A webhook receiver answering with an error status is now recorded as a failed delivery instead of a success.

**Fixed: the generated AWS deployment runs (#407, #423).** The generated AWS Terraform stack now includes the ECS service and network it needs, applies cleanly and boots.

**Changed: a build fails clearly when Storybook tests are enabled but the runner cannot run them (#308).**

**Fixed: Puppeteer runner cleanup (#388, #405).** Shared CDP browsers are disconnected without closing the remote Chrome, and a cancelled first launch is released before the server does more work.

**Fixed: Storybook titles with slashes resolve correctly in the app (#326), and vulnerable dependencies are updated (#334).**

**Fixed: the `observability` and `ai` span wrappers no longer record raw errors (#466).** A database, storage or AI-provider error whose message held a connection string with a password, a token or a provider response was recorded as is on exported spans. Both wrappers now record a copy with the same name and a redacted message and stack, and only `HTTP <status>` for an `HttpError`, and still rethrow the original error. Together with #429, no span records a raw error.

**Fixed: webhook delivery no longer buffers the receiver's response body (#430).** A new `httpStatus` helper in `@storyshelf/core/utils` shares the retries, timeouts, redaction and tracing of the other HTTP helpers but never reads the body: it cancels it on every response. Webhook delivery uses it, so a receiver that answers with a huge body cannot grow the server's memory. An `HttpError` from `httpStatus` has an empty `body`; the signature and the delivered/failed outcomes are unchanged.

**Fixed: spans no longer record response bodies or full URLs of outbound requests (#429).** `withSpan` now records a redacted copy of a thrown error (same name, `redactSecrets` message) and rethrows the original object, for every span in core. A failed outbound HTTP request is recorded as `HTTP <status>` with `http.response.status_code`, never the response snippet, which could echo the request URL in any encoding; the `HttpError` a caller catches is unchanged. `redactUrlForLog` now returns the origin only (`https://api.telegram.org`), replacing "origin plus first path segment", because for some APIs that segment is the credential (a Telegram bot token). This applies to `url.full` and to retry and request logs. A request that `fetch` refuses because of userinfo is recorded with the URL replaced by its origin.

**Fixed: measuring a remote browser's environment is bounded and cancellable (#273).** The probe that fingerprints a remote browser (version, OS, pixel ratio, fonts) had no time limit and a cancel could not interrupt it, so an unresponsive service could hold a render, and a build cancelled during the probe could carry on as a normal capture with an unknown environment. It is now bounded by the new `timeouts.probeMs` of `remote()` and of the leased form of `cdp()` (default 15 000 ms; the other presets use the default). An overrun or a failure leaves the environment unknown with a warning, as before for a failure, and the render goes on. A cancel stops the run at once with `Capture cancelled`, closes the probe page, and releases the lease as `cancelled` (the Playwright runner released it as `failed`). Both runners share `boundedProbe` from `@storyshelf/core/utils`.

**Added: opt-in browser caching of capture-scoped signed Storybook assets (#385).** `config.captureAssets.cacheMaxAgeSeconds` (a whole number from 0 to 3600, default 0) lets a remote capture browser reuse a render's assets across stories instead of fetching them for every story. It is off by default and signed answers stay `Cache-Control: private, no-store`. When set, a successful answer for a token the server minted for a render pass (a new signed `capture` purpose claim; tokens minted before it, and interactive preview links, are unchanged and verify as before) for a file of a content-addressed build is `private, max-age=N`, N being the least of the cap, one hour and the token's remaining lifetime, so it never outlives the grant. Errors, refusals, previews and legacy files stay `no-store`; the server sets the header and runners get a URL only. Authorization is still checked on every request that reaches the server, but bytes a browser already holds fresh cannot be recalled until their freshness ends, and a fresh browser context starts cold. See the remote browsers guide.

**Changed: accessibility checks warn when story configuration contains values that cannot cross from the preview (#242).** The warning includes the story ID and omitted-value count; axe uses the remaining configuration.

**Changed: invalid inline Storybook ZIP uploads return 422 (#253).** Malformed, unsafe or over-limit archives are rejected immediately without queuing capture; a corrected archive can be uploaded to the same build. Background publishing remains asynchronous.

**Fixed: a signed Storybook URL lifetime that cannot fit a capture fails the build once.** The "lifetime too short" and "story too large for a slice" errors are now a `SignedUrlLifetimeError`: crash isolation no longer treats them as a story crash, and the capture job is not redelivered, since another try would fail the same way. The build is failed with the message that says to increase or clear the project override.

**Fixed: Storybook interaction tests now wait for their completion event.** A rendered story is no longer reported as a passing test while its asynchronous test body is still running.

**Fixed: signed Storybook URLs no longer expire before their render timeout.** Render passes honor the configured token lifetime, using smaller slices and shorter timeouts when necessary. A legacy override too short for a capture or an unsplittable story now fails with guidance to increase or clear it.

**Breaking: custom database adapters must implement `updateWhere` (#293).** The condition must be evaluated in the same database statement as the update; it returns the current row, or null if the row is absent. Capture status updates use it to prevent a late write from overwriting a cancelled build. The built-in SQLite, PostgreSQL and MySQL adapters implement the operation.

**Fixed: the System page no longer asks an admin to confirm an origin that `PUBLIC_BASE_URL` or the platform already sets (#315).** When the configuration or the hosting platform answers, the public origin card shows that origin with "Nothing to confirm" and offers neither the confirm form nor the manual entry form, and the page stops reporting the browser's address. `POST /admin/public-origin/report` answers `204` and stores nothing, and `POST /admin/public-origin` refuses with a message naming `PUBLIC_BASE_URL`, so a visit through another domain can no longer leave a stale unconfirmed origin behind. An origin an admin confirmed is unchanged.

**Breaking: `remote()` declares `protocol` and `reach`, and takes one `connect` with a lease, `release` and `refCounted` (ADR 0007, decision 4; #316).** A remote service that must be woken, started or chosen per shard (a self-hosted Playwright server on a computer billed only while it runs) no longer needs a proxy in front of it. `remote()` now requires `protocol` (`"playwright"` or `"cdp"`) and `reach` (`"loopback"`, meaning Playwright's `exposeNetwork: "<loopback>"`, or `"url"`), both declared and never inferred from a sample connection. `connect` is a fixed `{ endpoint, headers }` object, validated when the runner is created, or a function (sync or async) called for every connection with `{ engine, buildId, runId, shardIndex, purpose, attempt, signal }` that returns `{ endpoint, headers, lease }`. `shardIndex` is the shard's 1-based position and `undefined` (never 0) when the build is not sharded; `purpose` is `render`, `extract` or `tests`; `signal` aborts a `connect` still pending on `timeouts.acquireMs`, a cancel (user, build, render budget) and shutdown. `release(lease, { outcome, error })` runs exactly once per lease with `finished`, `failed` or `cancelled`: after a render, on a failed handshake before the retry connects again, on a cancel, and for leases still held at shutdown. It is awaited under `timeouts.releaseMs` (default 30 s); a throw or a timeout is logged by error class and never fails the render, and it is skipped, with one warning per target, when `connect` returns no lease. `RemoteConnectError(message, { transient, scope, lease })` says how a failure is treated: `transient: false` stops the retries and marks the target unavailable until restart, `scope: "job"` fails only the job and keeps the target offered, and a `lease` on the error is released as `failed`. `refCounted({ open, close, idleMs })` shares one resource between connections (opened by the first, closed `idleMs` after the last, at once on shutdown; a `close` that fails leaves it unknown so the next connection opens it again). `remote<TLease>` types the lease. `lifecycle.teardown()` of both runners calls the new `shutdownRemote()`: pending connects are aborted, held leases released as `cancelled`, pools closed. `sessions` may be a function, read live; a value that is not a finite number keeps the last good cap and logs once, and a cap that grows now lets in every waiting page on the next release. The lease credentials are scrubbed from every error and never logged, stored or put on a span. **Migration:** `connect: (engine) => ({ protocol, endpoint, exposeNetwork })` becomes `protocol`, `reach` and `connect: { endpoint }` (or a function); `connectRetries` and `connectBackoffMs` become `retry: { attempts, backoffMs }`; `connectTimeoutMs` becomes `timeouts: { connectMs }`; unknown or removed options throw when the runner is created and name their replacement. `playwrightServer`, `azurePlaywright`, `browserstack` and `cdp` keep their options. The Puppeteer runner's `cdp()` takes the same function `connect`, `release`, `retry` and `timeouts` (CDP is Chromium only, so its `reach` is always `url`), and both runners' `./remote` subpaths export `RemoteConnectError` and `refCounted`. Docs: the remote browsers guide gains **Scale to zero** and **Upgrading from 0.7**.

**Changed: signed Storybook URLs follow the owner's review (ADR 0007, decision 5; #275, #255).** The route and the minted URL move from `/s/<token>/` to `/_s/<token>/` (`STORYBOOK_TOKEN_PREFIX`, one constant for the auth gate, the route table, `redactSecrets` and the minted URLs; it cannot meet the `/_/:id` short link). **Added: signed Storybook URLs for remote browsers that cannot route back (ADR 0007, decision 5; #228).** A `reach: "url"` target (every Puppeteer remote target, CDP-only services, BrowserStack) now renders: for each render pass and for the parameter pre-pass the job mints `<publicOrigin>/s/<token>/` and passes it as `storybookUrl`. **Added: remote browsers (ADR 0007, decisions 1 to 5; #226).** The runners can connect to a browser on another machine instead of launching one. `@storyshelf/runner-playwright/remote` exports `remote({ name, engines, connect, sessions })` and the presets `playwrightServer` (a self-hosted `playwright run-server`, `exposeNetwork` on by default), `azurePlaywright` and `browserstack`; `@storyshelf/runner-puppeteer/remote` exports `cdp`. They go in the runner's `browsers` list and offer one `<engine>@<name>` target per engine (`chromium@grid`) with its own baselines, never compared with a local render. Presets are plain configuration (no vendor SDK) and validate when the runner is created: a bad name, an engine the connection cannot serve, a non-WebSocket endpoint or two entries with one target throw. Playwright uses `browserType.connect(endpoint, { headers, exposeNetwork })` (or `connectOverCDP` for a CDP connection), Puppeteer `puppeteer.connect`; with `exposeNetwork: "<loopback>"` the remote browser reaches the loopback Storybook server through the connection, so such a target needs no public origin. The environment of a remote render is measured inside the browser (browser version, OS, device pixel ratio and a digest of a fixed 44-font probe list), never from the host, so a provider-side image change is diffed and not waved through as an environment migration. A target's `sessions` is its page cap, shared per target across the process (`sessionGateFor`; an explicit `concurrency` can only lower it). Connection-level failures (refused, dropped, timed out, no capacity, 429 and 5xx) are retried with exponential backoff before the render or crash isolation sees them; what is left fails the job at once as a `TargetLaunchError`, which carries the new `transient` flag (a service that is merely down stays offered; refused credentials and a Playwright version mismatch, which names both versions, mark the target unavailable). Endpoints, query values and header values never appear in messages or logs. `render` and `extractParameters` accept `storybookUrl`, the URL a `reach: "url"` target's browser opens instead of the loopback server; nothing mints it yet, so such targets (BrowserStack, every Puppeteer remote target) cannot render until signed Storybook URLs (#228). New guide "Remote browsers" with the self-hosted farm setup, pinned to the `playwright-core` version (a test fails when the page drifts) and what a bare `run-server` guards: no authentication (the `--path` is the only gate) and `--max-clients` queues extra connections instead of refusing them. `CaptureEnvironment.platform` is the browser's OS for a remote render. The `test:integration` suites of both runners now run a remote capture against a real `run-server` (Playwright) and a separate Chrome over CDP (Puppeteer).

**Added: build state on git channels is a function of the build, delivered by durable `notify` jobs (ADR 0014, decisions 5 to 7; #221, #222).** One pure function, `statusesForBuild` (`@storyshelf/core/adapter/notifier`), maps a build, the channel's prefix and the `testing`/review flags to the states a git channel shows: `<prefix>/testing` (`pending` while capture runs and review is open, `success` when approved, `failure` when rejected or capture failed, the description saying whether review is open), `<prefix>/storybook` for every build with a commit (informational: `success` linking the published Storybook once its manifest exists, `failure` for a failed build that never published) and one pull-request comment per build with links to the build and the Storybook plus a summary. `<prefix>/review` is in the function for the review setting to feed (`flags.review`). The website's capture, deployment and configuration pages describe `testing`, hosting only and the database queue, and carry the long-running-server requirement.

**Breaking: the app consumes the database queue; the in-memory capture queue, the boot sweep and the stall handler are gone (ADR 0006, decisions 4 and 5; #217).** `createShelfApp` wires ONE database queue (`capture_jobs`) and ONE consumer for every job kind (`capture` with `testing`, `publish` on a long-running host). Uploads enqueue onto it and the instance's consumer wakes at once; every instance with `testing` consumes. `InMemoryCaptureQueue`, `recoverStuckCaptures`, `recoverStalledCapture` (`INTERRUPTED_ERROR`, `STALLED_ERROR`), the app's stalled-capture handler and the boot requeue of `capturing` builds are deleted without a replacement: lease expiry and redelivery recover work, so two instances can start without resetting each other's builds, and a job whose last attempt lost its lease fails its build (`DatabaseCaptureQueueOptions.onExhausted`). New `testing.retries` (default 2) is the one retry limit for failed attempts, lost leases and forked-child crashes; `testing.queue` is now a `PollableCaptureQueue` that replaces the database queue and, with a `runner`, is consumed in-process too. `capturesLocally` is replaced by the store's `capturesHere`.

**Breaking: forked capture is parent-push (ADR 0006, decision 5; #217).** The app consumes the queue and pushes each leased job to the `testing.workerEntry` child over IPC (`run`/`cancel` down, `progress`/`done`/`failed` up); the child never reads the queue and inserts shard jobs into the database queue itself. `ForkedCaptureQueue`, `IpcCaptureQueue` and the `poll`/`enqueue`/`ack`/`nack` messages are deleted; `createForkedCaptureHandler` and the new protocol replace them. The concurrency slots live in the parent, so `STORYSHELF_CAPTURE_CONCURRENCY` no longer reaches the child (`STORYSHELF_CAPTURE_RETRIES` does). `runCaptureChild` now lives in `core/src/capture/forked/child.ts` (same export).

**Added: `testing` gates the app; hosting-only mode (ADR 0006, decisions 1 and 3; #216).** The app store now carries a real `testing` flag (`options.testing` is set) instead of inferring it from the capture queue. Without it, every route the route table classifies `testing` answers `404` (`Testing is not enabled on this instance.`; JSON on `/api/v1`, text on pages) through the new `requireTesting` middleware, mounted ahead of the CSRF and rate-limit guards; `hosting`, `both` and `review` routes are untouched. The navigation drops the Jobs entry and the capture, tests, git status and AI settings tabs; the System page shows a hosting-only notice with the number of hidden snapshots; boot logs the mode (a warning with `hiddenSnapshots` when snapshots exist); `POST /api/v1/projects/:slug/builds` returns `testing`, and `storyshelf upload` prints that no checks will run and skips the affected-capture post when it is `false`. `testing` now needs `runner` or `queue` (`testing: {}` throws). New `assertServerless` (`@storyshelf/core/config`): a process with `testing.runner` throws on AWS Lambda, warns on Vercel and Netlify, and `STORYSHELF_ALLOW_SERVERLESS=1` overrides it; `isServerlessHost` moved to core. Database metadata gains `supportsTesting`; the Cloudflare D1 preset sets it to `false`, and `createShelfApp` refuses `testing.runner` on it. A remote-queue-only instance (`testing: { queue }` without `runner`) is exempt from both checks. New concept page "Hosting only".

**Added: the Storybook catalog, and library, component and build pages that render from it (ADR 0006, decision 9; #215).** When publishing ends, the build's `index.json` is read into a compact `catalog.json` (next to the build's files) and one `build_components` row per component (project, build, story file, title, story count, hash; new table in all three database packages, purged with the build). A build published before the catalog existed is catalogued on first view. The library shows the components of the latest build of the selected branch whatever its status; the component page gains a **Stories** tab (a click-to-load preview, sandboxed with `allow-scripts` only, and every story and docs entry) and a catalog **History** (added, removed, renamed); the build page shows component and story counts and labels an accepted build with no attempts **Published**. All of it works without `testing`; with it the pages gain thumbnails, statuses, States, design and linked packages, and snapshot sections. Published Storybook files answer `Access-Control-Allow-Origin: *` for builds viewable without credentials (public builds, instances without sign-in) so the sandboxed frame can load; private builds under sign-in are not embedded. Upstream links fall back to the catalog when a build has no snapshots.

**Added: publishing independent of capture (ADR 0006, decision 10; #213).** An instance without `testing` now
publishes Storybooks of any size. A zip up to `maxInlineUnzipSize` (now defaulting to 50 MB, counted while the
upload streams instead of read from `Content-Length`) is extracted inline; a larger zip becomes a `publish` job
on the database queue, run by a consumer that every instance with a database starts at `lifecycle.setup()` and
drains at `teardown()` (capture shares the queue since #217). The file-by-file route (`/dedup`, `/content`, `/manifest`)
completes publishing when the manifest is stored. On serverless hosts (`AWS_LAMBDA_FUNCTION_NAME`, `VERCEL`,
`NETLIFY`) no consumer runs, and an over-limit zip is refused with `413` pointing to the file-by-file route;
`storyshelf upload` now falls back to that route by itself (the old `tryDedupUpload` stub is gone).
Extraction is capped by the new `maxZipEntries` (default 50 000) and `maxUnzippedBytes` (default 2 GiB), counted
while streaming, and refuses absolute and `..` paths; `maxInlineUnzipSize: 0` sends every zip to a job. When
publishing ends with no capture to run, a published build on the project's default branch becomes `approved`, a
failed publish makes it `failed`, and other branches stay `pending`; no approval event or webhook fires. With
`testing` on, capture still sets the status. `config.scratchDir` now always defaults to
`<os.tmpdir()>/storyshelf`. `PublishCompleter` runs `afterPublish` hooks for the catalog. The one-time boot task
that would re-process builds already `pending` is dropped (no data migrations): such builds stay as they are.

**Added: `createDatabaseCaptureQueue` (`@storyshelf/core/capture`), a database queue on the new `capture_jobs` table (ADR 0006); additive, not wired in yet (adapters gain `tables.captureJobs`; `LeaseRenewal` gains `"cancelled"`; queues may add `cancel`/`inspect`).**

**Added: `createCaptureConsumer` (`@storyshelf/core/capture`), the consumer loop for any pollable queue (handler per job kind, slots before polling, retries with backoff, lease by progress, cancel, drain on stop; optional metrics hooks). `runCaptureChild` moves into core and `@storyshelf/worker` re-exports it. Retention purge also drops finished `capture_jobs` rows and a removed build's job rows. Not wired into the app yet.**

**Breaking: `ShelfOptions.capture` is now `ShelfOptions.testing` (ADR 0006).** The option, its type
(`ShelfCaptureOptions` is now `ShelfTestingOptions`) and its error messages are renamed, and the
top-level `compare` and `images` options nest under it, so the shape is `testing: { runner, queue?,
concurrency?, workerEntry?, shardSize?, mode?, compare?, images? }`. `config.scratchDir` stays where
it is. There is no alias or boot-time error for the old keys: rename them in your server, and
`storyshelf server init` now emits `testing: { ... }`. Behaviour is unchanged; `runner` stays
optional for now. Separately, `packages/app/src/routes/classification.ts` now classifies every
registered route as `hosting`, `testing`, `review` or `both`, and a test fails on any unclassified
or stale route (classification only, nothing is gated yet).

**Changed: accessibility checks are on by default and visible in review (ADR 0004 §6).** `runA11y`
now defaults to on for new projects (no migration: an existing database keeps the stored value) and
a project admin can turn it off in Settings > Tests or with `runA11y` on the project API (create,
read, PATCH, OpenAPI). The axe findings are no longer only in the runner log: each capture's
violation lines are stored on its snapshot (`snapshots.a11y_violations`, JSON array, new nullable
column in the DDL; exposed as `a11yViolations` in the snapshot API) and shown on the snapshot review
page, in the filmstrip and on the component page. They still never block a build or change a
status. The default rule set is now the WCAG A/AA tags plus axe's `best-practice` tag (an explicit
`parameters.a11y.options.runOnly` still replaces it); the page-level best-practice rules do not fire
for the default `#storybook-root` scan, so no rule is disabled. The MCP server and the CLI do not
mirror other project settings and do not expose it. Fixtures gained a `BestPractice` story.
**Added: axe-core accessibility checks (ADR 0004 §6).** With `runA11y` on, the Playwright and
Puppeteer runners now run axe-core over `#storybook-root` before the screenshot instead of the old
hand-rolled DOM scan (removed, with no fallback). Each violation is one `a11y:` annotation with the
rule id, impact, help text, a short selector and the node count (at most 10, then `…and N more`).
Stories' `parameters.a11y` is honoured (`disable`, `test: "off"`, `config`, `options`,
`element`/`context`; JSON-serialisable values only). If axe cannot run, the story gets one
`axe unavailable` annotation. Results stay non-blocking and never fail a build. `axe-core` (pinned)
is a dependency of `@storyshelf/core` only; the runners reuse it through `@storyshelf/core/capture`.
The fixtures gained `Components/Accessibility` stories and the Puppeteer runner a gated axe test.
**Fixed: environment migrations and the screenshot sweep (ADR 0031 phase 4).** A feature-branch
build no longer auto-accepts snapshots whose capture environment differs from the baseline's: it
diffs them, and a difference is `changed` with the environment change shown on the review page.
The default branch still migrates without a diff. Fingerprint components a capture did not report
(screenshots spooled before a browser crash, a failed `fc-list`) are unknown rather than changed
and never overwrite the baseline's, and a viewport size change diffs instead of migrating. The
screenshot sweep defers deletions while a build of the project is still capturing or a baseline
import or approval holds a reuse claim, so it can no longer delete an object a capture has just
reused. Local storage writes are atomic (temp file + rename) and `list()` returns `/`-separated
keys on every host. `sweepScreenshotContent` now needs `tables.builds`.

**New: `@storyshelf/image` and an opt-in `sharp` image engine (ADR 0032).** The pixel diff, its
worker pool, overlay rendering and AI thumbnails moved into the new leaf package
`@storyshelf/image` (`@storyshelf/core/diff` re-exports it). `pixelmatch` stays the comparator;
the PNG codec is selectable: `createShelfApp({ images: { engine: "sharp" } })` or
`STORYSHELF_IMAGE_ENGINE=sharp` (the option wins), with `pngjs` the zero-dependency default.
`sharp` is an optional peer: install it yourself, and startup fails clearly when it is missing.
Remote workers take the same `images`/`compare` options on `createCaptureWorker`, and forked
capture children inherit them from the server. See the "Image engines" guide.

**Upgrading (image engine):**

- `diffImages` and `buildTriageEvidence` now return Promises (the `sharp` codec is async): `await`
  them. Code that read `diffImages(...).passed` synchronously now reads `undefined`.
- `configureDiffPool({ threads })` is deprecated in favour of `configureImages({ engine, threads })`;
  the old name still works.

**Breaking: Figma is now a design-provider adapter.** Figma support moved out of core into

**Upgrading:**

- The component page's Figma tab is now `?tab=design`.

**Connect your own account:** when a project has no design token, signed-in members can connect
their own Figma account for previews (ADR 0030). Set `FIGMA_CLIENT_ID` / `FIGMA_CLIENT_SECRET`
(a Figma OAuth app with redirect `<publicBaseUrl>/connections/figma/callback`, scope

`createFigmaDesign({ oauth: figmaOAuthFromEnv() })`. The flow, token storage
(`user_connections`) and refresh are service-neutral (`@storyshelf/core/adapter/oauth`), so other

**Added:** `@storyshelf/core/adapter/design` (`DesignProvider`, `DesignClient`,
`parseDesignUrl`), `designContractSuite` in `@storyshelf/core/test-helpers`, and a per-viewer
cache scope (`design_nodes.viewer_id`).

**Fixes**

- The Puppeteer runner now runs `play` functions on Storybook 8, 9 and 10 (it failed with `Cannot call fromId/raw() unless you call cacheAllCSFFiles() first`), by loading just the story and running its `playFunction` with the mounted render's context, as the Playwright runner already does.

**Attempt logs**

- The build attempt log no longer stops at "partitioned" during a render. Per browser engine it now records the partition counts, the runner's `info`/`warn`/`error` lines (`capture sizing`, `browser recycled`, `render failed for story`, a11y warnings; debug stays out), `captured N/M screenshots` every 10 screenshots, and a `render pass finished` summary. Lines are written serially so order and sequence numbers stay correct under parallel rendering.

**Streaming and page reuse**

- Screenshots are written to storage as each is captured (new optional `onCapture` on `CaptureRunner.render`; both bundled runners support it), so memory no longer grows with the number of stories. Runners that ignore it keep working unchanged.
- Opt-in page reuse (`reusePages` / `STORYSHELF_REUSE_PAGES=1`) for both runners: pooled pages in their own contexts, reset between captures, discarded after a failure. Screenshots were byte-identical with reuse on and off on the bundled fixtures.

**Capture memory**

- Capture no longer opens a browser page for every story and viewport at once, which ran 500-story Storybooks out of memory on 1 GB hosts. Pages render with bounded concurrency, and snapshot persisting is capped at 4 at a time.
- Capture concurrency defaults are sized from the CPU and memory the process can use, container limits included (0.5 vCPU / 1 GB renders one page at a time; `ShelfConfig.captureConcurrency` defaults to 1 build unless the host has ≥ 2 CPUs and ≥ 3 GB). Override with `concurrency` on `createPlaywrightCaptureRunner` or `STORYSHELF_CAPTURE_CONCURRENCY`.
- Page navigation timeout scales up on CPU-starved hosts (60 s under 2 CPUs, 90 s under 1 CPU; override with `navigationTimeoutMs` or `STORYSHELF_NAVIGATION_TIMEOUT_MS`), so slow Storybook loads are not reported as failures.
- Chromium launches with low-memory flags (`--disable-dev-shm-usage`, `--disable-extensions`, `--disable-background-networking`, `--mute-audio`) to avoid crashes on small container `/dev/shm`.
- `@storyshelf/worker` sizes `concurrency` from the host the same way (1 capture, or 2 with ≥ 2 CPUs and ≥ 3 GB) instead of a fixed 2, and `DEFAULT_WORKER_CONFIG` no longer carries `concurrency`. Scaffolded workers pass `WORKER_CONCURRENCY` only when set.
- The per-render time budget scales with the number of captures (15 minutes minimum, 15 seconds per capture), so slower one-page-at-a-time captures on small hosts are not cancelled as timed out. An explicit `renderTimeoutMs` is unchanged.
- Both runners restart the browser every 150 captures (`recycleBrowserEvery` / `STORYSHELF_BROWSER_RECYCLE_EVERY`, `0` disables) and log a `capture sizing` line with the detected CPUs, memory and resulting settings at the start of each render.
- The Puppeteer runner gets the same bounded concurrency, automatic sizing, timeout scaling and low-memory launch args as the Playwright runner.
- Storing a build's Storybook statics now reads, hashes and uploads files with at most 8 in flight instead of reading every file into memory at once.
- The Fly demo app uses the automatic sizing (optional `CAPTURE_CONCURRENCY` override) and caps the Node heap with `NODE_OPTIONS` in `fly.toml`.

## 0.6.2 — Lean scaffold, working Docker images, Node 24 (2026-10-08)

A fix-focused release. `storyshelf server init` now generates a smaller
`src/`-based project with a `tsconfig.json`, and its Docker images actually
start; `npx storyshelf` starts faster and reports the right version; and a
server that opts out of auth no longer fails to bundle.

**Upgrading:** Node 24 is now the minimum supported version (every package
declares `engines.node >=24`, and generated projects require it). Existing
scaffolded projects keep working and are not rewritten; regenerate to get the
new layout and fixed Dockerfiles.

**CLI startup**

- Command modules and their dependencies (the zip library, prompts) now load only
  when that command runs, so `storyshelf -h`, `whoami` and the rest start in
  about 10 ms over bare Node instead of about 55 ms.
- `storyshelf --version` reports the real package version (it was hardcoded to
  `0.2.0`).
- Dropped the unused `hono` dependency from the CLI, so `npx storyshelf`
  installs less.

**Node 24 is the minimum**

- Every published package declares `engines.node >=24` (none did before), the
  release check fails if one does not, and the docs, README and CI example now
  say Node 24 instead of 22 or 20.
- The slim server image is pinned to `node:24-alpine` instead of the floating
  `node:lts-alpine`.

**First-run and release safety**

- `@storyshelf/db-sqlite` creates the database file's directory (all file-based
  presets), so a fresh scaffold or an empty Docker volume boots instead of
  failing with `unable to open database file`.
- CI now smoke-tests the built artifacts: the CLI launched through a `.bin`
  symlink (as `npx` does), and a freshly scaffolded server that type-checks,
  boots, serves HTML and vendored assets, and shuts down cleanly. The two
  regressions that shipped in 0.6.0 and 0.6.1 would have failed it.
- Generated projects (`npm start`, `dev`, `worker`, the Docker `CMD`) and
  `storyshelf server serve` / `worker serve` no longer pass
  `--experimental-transform-types`, which Node 26 rejects (`bad option`). Node 24
  and later strip types without a flag, so entries run with plain `node`; the
  generated `package.json` declares `engines.node >= 24`.
- The npm publish job skips versions that are already published, so a partly
  failed release can be re-run (the JSR job already did this).

**CI**

- The whole pipeline now runs on Node 24, the minimum supported version
  (`devEngines.runtime` is `24.x`; it was `>=24`, which CI resolved to the
  newest Node). The smoke test asserts the Node major so the default cannot
  drift unnoticed.
- The website build, link check and accessibility check run only when
  `apps/website/` changed (scheduled and manual runs always run everything).

**`storyshelf server init` scaffold**

- Entry code now lives in `src/index.ts` (and `src/worker.ts`) so you can split
  logic into more files; `tsconfig.json`, `@types/node` and a `typecheck` script
  are generated so the editor resolves types. `storyshelf server serve` /
  `worker serve` find `src/` first and still run the older root layout.
- Leaner output: notifications and OpenTelemetry wiring are opt-in (the prompts
  now default to no), imports from the same module are merged, and unused
  variables and dependencies are no longer emitted.
- Docker: `compose.yaml` is only generated when the stack has more than one
  service (Postgres or a worker); a single container gets `docker:build` and
  `docker:run` scripts instead.
- Fixes: the generated Docker images could not run. They bundled the server
  with esbuild into one ESM file, which crashes at startup (`Dynamic require of
"util" is not supported` from a CommonJS dependency) and cannot find the
  vendored assets `@storyshelf/app` reads from disk; the `CMD` also pointed at
  a path the bundle was never copied to, and the build copied a `playwright`
  package that is never installed. Images now install production dependencies
  and run `src/index.ts` directly with Node (as `npm start` does), on a
  Playwright image pinned to the `playwright-core` version. With a worker, the
  compose worker service was written inside the `volumes:` block (invalid) and
  had no `DATABASE_URL`.
- **Heads-up:** the generated server file moved from `server.ts` to
  `src/index.ts`; existing projects keep working and are not rewritten.

**Packaging**

- `@storyshelf/app` no longer imports `@storyshelf/auth`, so a server that opted
  out of auth bundles and installs without it (it failed to resolve before). The
  shared `Auth` contract plus `MIN_PASSWORD_LENGTH` and `unsignedToken` come

**Server runtime**

- `@storyshelf/runner-playwright` loads `playwright-core` on the first render

- Shutdown waits (up to 5 s) for the stuck-capture recovery and credential check

**Auth: admin-token bootstrap, user-bound tokens**

- New `ShelfConfig.adminToken` (`STORYSHELF_ADMIN_TOKEN`/`ADMIN_TOKEN` env):

- API tokens are bound to their creating user (`tokens.user_id`) and resolve
  to that user's live project role; bearer callers are now subject to route
  role requirements. Legacy ownerless tokens resolve as viewer; tokens whose

- Project creation records the session creator as project admin.
- **Action required after upgrade:** re-create CI tokens used for

- New `project_group_mappings` table maps IdP groups to project roles per

  wins, removals revoke synced grants only, manual grants untouched).
- **Action required after upgrade:** run DB migrations for `project_members.source`
  and the new `project_group_mappings` table.

## 0.3.0 — Streaming uploads + webhook secrets (2026-09-06)

**Webhook secrets encrypted at rest (#45)**

- `webhooks.secret` (plaintext) is replaced by `secret_encrypted` (AES-256-GCM
  under `ShelfConfig.secret`). The legacy column is dropped by migration —
  pre-existing plaintext secrets are **discarded, not migrated**.
- **Action required after upgrade: re-create webhooks.** Until then, deliveries
  for old webhooks fail closed (skipped, never crash). Creation fails loudly
  when `SECRET` is unset.
- `WebhookModel` now takes the server secret (`new WebhookModel(db, secret)`);
  `DatabaseAdapter` no longer exposes top-level `migrate()`/`close()` (see
  #59 lifecycle); `emitWebhookEvent` takes the secret as its final argument.

**Streaming uploads replace multipart (#53)**

- `POST /api/v1/projects/:slug/builds` accepts only `application/json` and
  returns `{ build, uploadUrl }`; the bundle streams via
  `PUT …/builds/:buildId/zip` (new `StorageAdapter.writeStream/readStream`;
  `maxUploadBytes`, default 1 GiB, enforced with `413`). The multipart form
  route is removed — servers answer old CLI uploads with `4xx`.
- **Action required after upgrade: upgrade the CLI.** Old servers are not
  supported by the new CLI (no fallback); old CLIs cannot upload to new
  servers. The deprecated `--storybook-dir` alias is removed (use
  `--build-dir`); JSON creation accepts `labels: [{ key, value }]`, and the
  CLI gained repeatable `--label key=value`.
- Small zips persist Storybook statics inline at upload time.

**Adapters**

- Mandatory metadata category plus adapter lifecycle and two-tier health.

## 0.2.0 — Repository restructure (2026-09-05)

Internal reorganization with a small, documented public-surface cleanup. See
`docs/migration-0.2.md` for the import-path changes.

**Public surface (`@storyshelf/core`)**

- Barrel is router-only: `createShelfRouter` + option/config/app types. All
  values moved to subpaths (new entries: `core/logger`, `core/capture`,
  `core/adapter/capture-queue`, `core/paths`, `core/urls`, `core/diff`).
- Internal tooling (`store`, `middleware`, `retention`, pages) has no public
  entry and may change without notice.

**Core layout (`@storyshelf/core`)**

- `schema/` per-entity directory replaces `schema.ts` + `schema-tables.ts` (one module
  per entity, mirroring `models/`; DDL drift-guard test added).
- Barrel (`@storyshelf/core`) now also exports `models/*`, `middleware/*`, and the
  request `store`. Model modules no longer re-export row types.
- `index.tsx` (482→~250 lines): capture dispatch (`capture/dispatch.ts`),
  merge/dedupe skip checks (`capture/skip-checks.ts`), and middleware factories
  (`middleware/request-log.ts`, `store-scope.ts`, `auth-gate.ts`) extracted.
- Settings router split by tab area (`settings.handlers.ts` + `settings-*.ts`);
  `build-diff` page split into section components; `ui/components.tsx` is now a
  facade over `ui/{buttons,feedback,forms,layout}.tsx`.
- Test doubles moved to `test-helpers/` (never shipped); `status-fanout.test.ts`
  colocated with its implementation.

**Adapters**

- New `createDrizzleAdapter` factory (`core/adapter/database`); `db-sqlite` and
  `db-turso` are thin driver shims. Adapter tests gained exact type inference.
- `db-sqlite` runs on the `node:sqlite` builtin via `drizzle-orm/sqlite-proxy`
  — zero native dependencies (`better-sqlite3` removed). Same signature, same
  WAL mode, same schema.
- New shared `upsertReviewComment` flow (`core/adapter/git-host/comments`);
  `git-github` / `git-gitlab` comment modules are thin provider bindings.

**Apps**

- `dev-server` and `fly-app` stay separate launchers owning their own adapter
  wiring, so deployments can diverge (locals vs Turso/S3). Shared code lives in
  `packages/`, not `apps/` (a shared-assembly experiment was evaluated and
  reverted for exactly this reason). `apps/` packages are unversioned (the
  release script only versions `packages/`).

**CLI (`@storyshelf/cli`)**

- `create`/`init`/`upload` accept an optional `cwd` (test seam, backward compatible).
- Command test suite added (config, create, upload, init, retry, purge).
- All file-wide `oxlint-disable` headers removed (`index`, `config`, `create`,
  `init`, `upload` refactored into small helpers).

**Repo hygiene**

- `docs/repo-structure.md` added (annotated map; bundler rule: tsdown for libs,
  rolldown for apps); `AGENTS.md` / `README.md` drift fixed.
- `.oxlintrc.json`: deleted the `packages/core/src/**` wildcard and the hardcoded
  file list; legacy violations tracked per-file (see open issues) instead.
- `turbo.json` build outputs scoped to `dist/**`.
