StoryShelf can summarize a build ("is this change intended, does it need review, or does it look like a regression?") and produce a project health digest. Insights are **advisory only**: they never approve, reject, waive a failing `play` function, or override a changed baseline.

AI is **off by default**. It needs two switches: the server is given a model (site-wide), and a **site admin** picks an AI profile for each project (per project).

## 1. Give the server a model

Install `@storyshelf/ai` and a provider package of your choice, then pass the AI surface to `createShelfApp`. StoryShelf never sees your API keys; they live in your server assembly.

```ts
import { createAi } from "@storyshelf/ai";
import { createShelfApp } from "@storyshelf/app";
import { openai } from "@ai-sdk/openai";
import { anthropic } from "@ai-sdk/anthropic";

const ai = createAi({
  profiles: {
    default: { defaultModel: openai("gpt-4o-mini") },
    sensitive: { defaultModel: openai("gpt-4o-mini"), models: { vision: null } },
  },
  defaultProfile: "default",
  budget: { dailyTokens: 2_000_000, visionWeight: 5, perProjectCallsPerHour: 50 },
});

const app = createShelfApp({ database, storage, ai });
```

- **Profiles** are named data-flow decisions. A profile with `vision: null` never sends screenshots; a profile whose vision model is a cloud model does.
- **Models** can be a bare model or `{ model, maxTokens, vision, timeoutMs }`. Task slots are `triage`, `vision` (used by triage when screenshots are sent) and `health`.
- Pin the AI SDK major: `@storyshelf/ai` pins `ai` and `@ai-sdk/otel` exactly, and checks provider models at startup.

### Credentials

Use cloud-provider identity (Amazon Bedrock, Google Vertex, Azure OpenAI via IAM or managed identity), vendor API keys held as service secrets, an internal LLM gateway, or a local server such as Ollama. Consumer plans (a Claude or ChatGPT subscription used through Claude Code or Codex) are not supported: those credentials are issued for the vendors' own clients. Confirm your provider's terms for server use.

For a quick, cheap setup while evaluating, see [Free AI for testing](/guides/ai-testing/).

## 2. Turn it on per project

A site admin opens **Project settings → AI** and chooses a profile (or **Off**), or sets `aiProfile` with `PATCH /api/v1/projects/{slug}`. The choice decides which models see that project's data, so only site admins can change it.

<Screenshot name="ai-settings" alt="Project settings, AI tab: a select to choose the AI profile for the project" caption="Site admins choose which profile (and therefore which models) a project uses." />

With a profile set:

- the build review page shows an **AI triage** panel (approvers and admins can generate or regenerate it);
- the project **Library** and **Builds** pages show an **AI project health** panel (last 30 days) with a generate/refresh button for approvers and admins, and the project card on **Projects** shows a health badge once a digest exists;
- `/api/v1` exposes the endpoints below;
- an `insight:ready` notification is emitted when a result is ready (opt-in like every notification).

## What the model sees

Deterministic, size-capped evidence: build metadata, changed files, the changed snapshots ranked by difference, head and tail of warn/error capture logs, a few comments, and (with a vision profile) up to three downscaled screenshots. Secrets are redacted before anything is truncated or sent. Everything from your Storybook is treated as untrusted data: it is fenced in the prompt, the answer is validated against a fixed schema, and all text is rendered as plain text.

## API

| Method | Route | Roles | Notes |
|---|---|---|---|
| `GET` | `/api/v1/projects/{slug}/builds/{buildId}/insights/latest` | all | `404 never-generated` until the first run; carries `status` while running |
| `GET` | `/api/v1/projects/{slug}/builds/{buildId}/insights` | all | Bounded history (`?limit`) |
| `POST` | `/api/v1/projects/{slug}/builds/{buildId}/insights` | approver, admin | `{ force?, profile? }`; `200` cached, `202` started (poll `latest`). `profile` is honoured for site admins only |
| `PATCH` | `/api/v1/projects/{slug}` | site admin | `{ aiProfile }`: a configured profile name, or `null` to turn AI off |
| `GET` | `/api/v1/projects/{slug}/insights/health?window=30d` | all | Cached digest |
| `POST` | `/api/v1/projects/{slug}/insights/health` | approver, admin | `{ window? }`; on demand, no scheduler |

Guard order: `501 ai-disabled` (no AI on the server) → `409 ai-disabled-for-project` → role → `429` (budget or rate limit, with `Retry-After`). Identical evidence is served from cache at no cost; `force` re-runs.

## Budget and usage

`budget.dailyTokens` is a site-wide cap per **UTC day**, counted from usage rows in the database, so it holds across multiple server instances (concurrent calls can overshoot slightly). Calls that include screenshots count `visionWeight` times. At 100% new runs get `429` until the next UTC day; cached results are still served. Site admins get a `sys:ai-budget` notification at 50%, 75%, 90% and 100%. **Admin → System → AI usage** shows tokens by day and profile. Usage rows and health digests are kept 90 days.

## Observability

With OpenTelemetry enabled, each call emits an `ai.summarize` span (with the SDK's GenAI spans beneath it) and bounded metrics; prompts, screenshots and outputs are never recorded. See [Observability](/guides/observability/).
