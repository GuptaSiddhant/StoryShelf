Scaffold and operate a self-hosted StoryShelf server. For the cloud Terraform modules see [Deployment](/guides/deployment/).

## `create-storyshelf`

Scaffold a new server project (`npm create storyshelf`, or `npx create-storyshelf`; `pnpm create storyshelf`, `yarn create storyshelf` and `bun create storyshelf` work too). The `create-storyshelf` package has no dependencies and is separate from the `storyshelf` client CLI:

```bash
npm create storyshelf
# ? Project name? my-storyshelf
# ? Directory? ./my-storyshelf
# ? Which database? SQLite
# ? Which storage? Local filesystem
# ? Which auth? None
# ? Which git provider? GitHub
```

Generates a small TypeScript project in the target directory:

```
src/index.ts      # the server: it also runs the captures (database queue, no worker)
package.json
tsconfig.json     # editor types; `npm run typecheck` runs tsc
Dockerfile        # only if you choose Docker
compose.yaml      # only when the Docker stack has more than one service
```

The entry is a `defineShelfInstance` module that `storyshelf-server` loads. Entry code lives in `src/` so you can split logic into more files (use `.ts` in relative imports). The Docker image installs production dependencies and runs `src/index.ts` directly with Node, the same as `npm start`; there is no build step. A single-container setup (for example SQLite + local storage) gets `docker:build` / `docker:run` scripts and no compose file; compose is generated when the stack adds Postgres.

Notifications and OpenTelemetry wiring are opt-in: the generated server only imports what you selected, so the default output stays short.

`--install` runs the install with the package manager that launched it (read from `npm_config_user_agent`); without it nothing is installed and the next steps say what to run. `--dir <path>` picks the output directory.

**Deploy targets** (when prompted, `local` or `docker`):

- `local` — bare Node
- `docker` — compose file + `docker:*` npm scripts

### `--cloud`: a Terraform module stub

```bash
npx create-storyshelf --cloud aws    # or gcp, azure
# ? Deployment name? storyshelf
# ? AWS region? us-east-1
# ? CIDR ranges allowed to reach the load balancer? 10.0.0.0/8
# ? Public domain? (empty skips DNS)
```

This writes three files and no application code, because the module deploys the published image:

- `main.tf` — a `module "storyshelf"` block whose `source` is `git::https://github.com/GuptaSiddhant/StoryShelf.git//deploy/terraform/<cloud>?ref=v<cli version>`, with the matching `image_version`;
- `terraform.tfvars` — your answers;
- `.gitignore` — `*.tfstate*`, `.terraform/` and `tfplan`, added to an existing file without duplicates. The state and the plan hold the generated secrets: keep the state in an encrypted remote backend, never in git.

Then run `terraform init`, `terraform plan -out=tfplan` and `terraform apply tfplan`. To upgrade, change the `?ref=` and `image_version` together. Add inputs from the module's README (`min_instances`, `max_instances`, an existing database, …) to `main.tf` as you need them. A stack generated by an older CLI moves over with the [migration guide](/guides/deployment/migrate-terraform/).

## `storyshelf-server`

The instance commands are the `storyshelf-server` bin of `@storyshelf/app`. Run it in the server project (`npm start` does for `serve`, `npm run dev` for `serve --watch`).

```bash
storyshelf-server serve [--port 3000] [--watch]   # start the instance; SIGTERM drains it
storyshelf-server migrate                         # run the database migrations, then exit
storyshelf-server purge [--ttl-days 30]           # purge expired builds
storyshelf-server check-storage [--sample 50]     # read-only consistency check
storyshelf-server doctor                          # installed packages and peers, module, settings, schema level
```

The project's `src/index.ts` default-exports an instance definition: configuration, never a constructed app.

```ts
import { defineShelfInstance } from "@storyshelf/app";

export default defineShelfInstance(
  async (env) => ({ database, storage, config: { adminToken: env.SHELF_ADMIN_TOKEN } }),
  {
    afterSetup: async ({ options }) => {
      /* needs the migrated database; only `serve` runs it */
    },
  },
);
```

`storyshelf-server` loads `.env` (the shell's variables win), refuses renamed settings, calls the factory and creates the app for the command. `serve` runs everything; `migrate` sets only the database up; `purge`, `check-storage` and `doctor` run as tools: they never migrate and start no job consumer, timers or replay, so the database must already be at this release's level (`doctor` reports it). A module that exports a constructed app is refused. An optional peer the module imports but you did not install (a database driver, a storage SDK) fails with the package or subpath that needs it, the range and the `npm install` line; `doctor` checks the installed `@storyshelf/*` packages before it imports the module and fails on mixed `@storyshelf/*` versions or a second copy of `@storyshelf/core`. `--entry <file>` or `"storyshelf": { "server": "<file>" }` in `package.json` names the module; without either the usual names are searched. `purge` and `check-storage` run in-process with the instance's admin token (`config.adminToken`, `SHELF_ADMIN_TOKEN`). `storyshelf server serve`, `storyshelf server check-storage` and `storyshelf purge` were removed without a replacement alias.

See [Getting started](/guides/getting-started/) for the full init flow and [Configuration](/guides/config/) for env vars.
