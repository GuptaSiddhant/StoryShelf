:::caution
The container image and the Terraform modules ship from the next release (v0.12.0). Until then, build the image from the repository's [Dockerfile](https://github.com/GuptaSiddhant/StoryShelf/blob/main/apps/server-image/Dockerfile), and pin the module to `main`.
:::

The Azure module in `deploy/terraform/azure` deploys the full product, the app plus capture, on Azure Container Apps. It deploys the published image and never builds one. It replaces `storyshelf server terraform-azure`; if you have a stack generated by that command, the [migration guide](/guides/deployment/migrate-terraform/) maps its resources to the module. The module's [README](https://github.com/GuptaSiddhant/StoryShelf/blob/main/deploy/terraform/azure/README.md) is the reference for names and defaults; this page explains the choices.

## Architecture

```txt
Internet ──▶ Container Apps environment (ingress, HTTPS)
                  │
                  └──▶ Container App (app + capture, min 1 replica)
                          │       │        │
                          │       │        └──▶ Blob storage (Storybooks, screenshots)
                          │       └──▶ Key Vault (secret references)
                          └──▶ PostgreSQL Flexible Server (private access)
                              Log Analytics           Managed identity (no keys)
```

- One container service runs the UI, the API and capture (the image bundles Chromium). Every copy also consumes the database queue, so scaling means more identical copies.
- Azure Database for PostgreSQL, Flexible Server is reachable only on private networking.
- The app signs in to Blob storage and Key Vault with one user-assigned managed identity. The storage account refuses shared keys.
- Secrets come from Key Vault as references, never as plain outputs.

## Use the module

Address the module by release tag through a git source, so an upgrade is a change of `ref`:

```hcl
module "storyshelf" {
  source = "git::https://github.com/GuptaSiddhant/StoryShelf.git//deploy/terraform/azure?ref=v0.12.0"

  name                = "storyshelf"
  location            = "eastus"
  image_version       = "0.12.0"
  allowed_cidr_blocks = ["203.0.113.0/24"] # your office or VPN; ["0.0.0.0/0"] publishes the app
}
```

The provider needs `features {}`, `storage_use_azuread = true` (see [Blob access](#blob-access)) and a subscription (`ARM_SUBSCRIPTION_ID`). Or let the CLI write this for you: `storyshelf server init --cloud azure` writes a module stub, a `main.tf` that uses the module at the CLI's own version, a `terraform.tfvars` with your answers, and a `.gitignore` for the state and plan, which hold the generated secrets (keep the state in an encrypted remote backend). Terraform is never applied for you: run `terraform init`, `terraform plan` and review it before `terraform apply`. Each release also attaches `storyshelf-terraform-<version>.tar.gz` for installs that cannot fetch from GitHub. To upgrade, change both versions together and read the release notes.

### Inputs

| Name                                                                              | Default                            | Meaning                                                                                                      |
| --------------------------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `name`                                                                            | required                           | Name prefix, 2 to 20 characters                                                                              |
| `image_version`                                                                   | required                           | Release version of the image (no `v`)                                                                        |
| `allowed_cidr_blocks`                                                             | required                           | Who may reach the app (the ingress IP restrictions)                                                          |
| `location`                                                                        | `eastus`                           | Region                                                                                                       |
| `image_repository`                                                                | `ghcr.io/guptasiddhant/storyshelf` | Registry path, for a mirror                                                                                  |
| `cpu`, `memory`                                                                   | `2`, `4Gi`                         | Capture renders in the container, so do not go much lower                                                    |
| `min_instances`, `max_instances`                                                  | `1`, `1`                           | Identical copies. At least 1. See [Running several instances](/guides/deployment/#running-several-instances) |
| `database_pool_size`                                                              | `10`                               | Connections per copy. `max_instances` × this must fit the database's limit                                   |
| `shutdown_grace_seconds`                                                          | `30`                               | Sets `SHUTDOWN_GRACE_SECONDS` and the termination grace (see [Shutdown](#shutdown))                          |
| `existing_database_url_secret_id`                                                 | `""`                               | A Postgres URL in Key Vault. No database is created                                                          |
| `database_sku_name`, `database_storage_mb`                                        | `B_Standard_B1ms`, `32768`         | Created database only                                                                                        |
| `deletion_protection`                                                             | `true`                             | Delete lock on the database, purge protection on the vault                                                   |
| `playwright_workspace_endpoint_secret_id`, `playwright_workspace_token_secret_id` | `""`                               | Optional Azure Playwright Workspace (secret references, both or none)                                        |
| `auth_email`                                                                      | `admin@example.com`                | Local admin login email (`AUTH_EMAIL`)                                                                       |
| `log_retention_days`                                                              | `30`                               | Log Analytics retention                                                                                      |
| `tags`                                                                            | `{}`                               | Added to every taggable resource                                                                             |

| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `url`                                                                                         | The app's HTTPS address on the Container Apps default domain |
| `resource_group_name`, `container_app_name`                                                   | For `az containerapp` commands                               |

## Permissions

`role_assignments` lists them. The app's identity has exactly:

| Role                            | Scope                          | Why                                    |
| ------------------------------- | ------------------------------ | -------------------------------------- |
| `Key Vault Secrets User`        | The module's Key Vault         | Resolve the app's secret references    |
| `Storage Blob Data Contributor` | The `storybook` Blob container | Read, write and delete Storybook files |

A secret in another vault (an existing database URL, a Playwright Workspace) needs `Key Vault Secrets User` for `identity_principal_id` on that vault; the module does not grant it. Terraform's own principal gets `Key Vault Secrets Officer` on the vault to write the secrets, then waits 60 seconds for it to take effect. The identity running Terraform needs `Owner` or `User Access Administrator` to create the role assignments.

Review these with your platform team before the first apply. They are also what you copy if you [adapt it to your own platform](#adapt-it-to-your-own-platform).

## Blob access

Blob access uses the app's managed identity, not an account key. The image gets `AZURE_STORAGE_ACCOUNT`, `AZURE_STORAGE_CONTAINER` and `AZURE_CLIENT_ID`, and signs in with `DefaultAzureCredential`. No connection string or account key is stored in Key Vault or passed to the app.

The storage account sets `shared_access_key_enabled = false`, so no account key or account SAS works against it, whoever holds one. The account keys and connection strings **remain in the Terraform state**, because the provider records them as computed attributes of the account, but they cannot be used. Keep the state in an encrypted backend anyway.

Terraform therefore manages the account through Azure AD: set `storage_use_azuread = true` in your `provider "azurerm"` block. The identity running Terraform also needs a data-plane role, because the provider reads the account's blob service settings through the data plane: grant it `Storage Blob Data Contributor` on the resource group or subscription **before the first apply**. The module cannot grant it. Operators who browse the container with `az storage` or the portal need the same role (`--auth-mode login`), not a key.

Outside Azure, the image also takes `AZURE_STORAGE_CONNECTION` (a connection string) instead. That needs an account that allows shared keys, so it does not work against this module's account.

## Database and secrets

- **Private database.** Postgres Flexible Server has no public endpoint. Only the VNet reaches it, through a private DNS zone. The module's URL says `sslmode=verify-full` and uses the server's FQDN, whose certificate chains to a public root, so the app verifies it with the system CAs. No live run has confirmed this yet. With your own database URL, see [Verify the database certificate](/guides/deployment/cloud/#verify-the-database-certificate).
- **Sign-in.** The module generates `AUTH-PASSWORD` and passes it with `AUTH_EMAIL` (default `admin@example.com`), so sign-in is on from the first boot. Read the password from the vault with `az keyvault secret show --vault-name "$(terraform output -raw key_vault_name)" --name AUTH-PASSWORD --query value -o tsv`.
- **Secrets.** `SECRET`, `AUTH-PASSWORD` and `ADMIN-TOKEN` are generated and reach the app as Container Apps secrets that are Key Vault references, resolved by the managed identity. Their values and the database password are also in the Terraform state, so keep the state in an encrypted backend with restricted access.
- **`OIDC-CLIENT-SECRET`** is an operator step. Terraform writes `change-me` once and never overwrites it. Put the real value in with `az keyvault secret set` and restart the revision. The image does not read OIDC settings yet.
- **Existing database.** With `existing_database_url_secret_id` the module creates no database, subnet or private DNS zone. The network path to that database is yours.

## Domain and TLS

The app is served on the Container Apps default domain over HTTPS. A custom domain and sign-in federation (Entra) are not part of the module.

## Keep one instance running and shutdown

The capture and notify consumers poll in the background, and Container Apps stops a scaled-to-zero app until a request arrives. The module requires `min_instances` of at least 1 (`min_replicas`): see [Keep one instance running](/guides/deployment/#keep-one-instance-running). Scaling is more identical copies up to `max_instances`, on concurrent requests.

### Shutdown

On a new revision the app gets SIGTERM and drains running captures for `SHUTDOWN_GRACE_SECONDS` (`shutdown_grace_seconds`, 30), then hands the rest back to the queue. The container's termination grace is the grace plus 10 seconds, so it is not killed mid-drain.

## Sizing and cost

For a small team (a few projects, a few builds a day) the defaults are the starting point: 2 vCPU and 4 GiB, one always-on replica, and a `B_Standard_B1ms` burstable Postgres server with 32 GB. Rough monthly cost is **150 to 220 USD** (an estimate, November 2026, for `eastus`: the always-on replica, the database, Log Analytics and Key Vault, plus storage and egress). Treat that as an order of magnitude and check the Azure pricing calculator for your region. Capture is the largest variable cost: Chromium needs about 100 to 300 MB per open page. See [Sizing memory for capture](/guides/deployment/#sizing-memory-for-capture).

## Backups

- **Database.** Flexible Server keeps automated backups; set the retention (up to 35 days) and use geo-redundant backup if you need it.
- **Storage.** Turn on blob versioning and soft delete on the storage account, so an overwritten or deleted blob can be recovered.
- **Key Vault.** `deletion_protection` keeps purge protection on; a destroyed vault stays soft-deleted for 7 days.
- **Order and restore.** Back up the database first, then storage, and restore both together. See [Back up and restore](/guides/backup-restore/), and run `storyshelf server check-storage` after a restore.

## Adapt it to your own platform

If your team won't use the module, you need three things:

1. **The image.** `ghcr.io/guptasiddhant/storyshelf:<version>` (`amd64` and `arm64`). It listens on port 3000 and bundles Chromium. Use at least 2 vCPU and 4 GB for capture and one replica minimum; the `-hosting` variant has no browser, for hosting without capture.
2. **The environment.** This is what the module passes:

   | Variable                                                              | Value                                                                                                         |
   | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
   | `AZURE_STORAGE_ACCOUNT`, `AZURE_STORAGE_CONTAINER`, `AZURE_CLIENT_ID` | The account, the container and the user-assigned identity. Setting another storage backend too stops the boot |
   | `PUBLIC_BASE_URL`, `TRUST_PROXY`                                      | The public `https://` origin, and `1` behind a proxy                                                          |
   | `SECRET`, `ADMIN_TOKEN`                                               | At least 32 random characters, the same on every copy (secret references)                                     |
   | `DATABASE_URL`, `DATABASE_POOL_MAX`                                   | A Postgres URL (the server's private hostname), and connections per copy                                      |
   | `SHUTDOWN_GRACE_SECONDS`                                              | Drain time on SIGTERM. Keep it below your platform's termination grace                                        |

3. **The permissions** in the section above, attached to the container's own identity. Never put cloud access keys in environment files, and turn shared keys off on the storage account.

Put a load balancer or ingress in front that terminates TLS and forwards the original host. Keep the database off the public internet.
