:::caution
The container image and the Terraform modules ship from the next release (v0.12.0). Until then, build the image from the repository's [Dockerfile](https://github.com/GuptaSiddhant/StoryShelf/blob/main/apps/server-image/Dockerfile), and pin the module to `main`.
:::

The GCP module in `deploy/terraform/gcp` deploys the full product, the app plus capture, on Cloud Run (CPU always allocated, so capture keeps running). It deploys the published image and never builds one. It replaces `storyshelf server terraform-gcp`; if you have a stack generated by that command, the [migration guide](/guides/deployment/migrate-terraform/) maps its resources to the module. The module's [README](https://github.com/GuptaSiddhant/StoryShelf/blob/main/deploy/terraform/gcp/README.md) is the reference for names and defaults; this page explains the choices.

## Architecture

```txt
Internet ──▶ Cloud Run service (app + capture)
                  │       │        │
                  │       │        └──▶ GCS bucket (Storybooks, screenshots)
                  │       └──▶ Secret Manager
                  └──▶ Cloud SQL Postgres (private IP, Direct VPC egress)
                      Artifact Registry (proxies ghcr.io)
```

- One container service runs the UI, the API and capture (the image bundles Chromium). Every copy also consumes the database queue, so scaling means more identical copies.
- Cloud SQL for PostgreSQL has no public IP and requires TLS (`ENCRYPTED_ONLY`), and the app verifies its certificate. Cloud Run reaches it by Direct VPC egress, and only private traffic uses the VPC.
- Cloud Run cannot pull from ghcr.io, so the module creates an Artifact Registry remote repository that proxies it (or you pass your own mirror as `image_repository`).
- Secrets come from Secret Manager as references, never as plain outputs.

## Use the module

Address the module by release tag through a git source, so an upgrade is a change of `ref`:

```hcl
module "storyshelf" {
  source = "git::https://github.com/GuptaSiddhant/StoryShelf.git//deploy/terraform/gcp?ref=v0.12.0"

  name          = "storyshelf"
  project_id    = "my-gcp-project"
  region        = "us-central1"
  image_version = "0.12.0"
}
```

Or let the CLI write this for you: `storyshelf server init --cloud gcp` writes a module stub, a `main.tf` that uses the module at the CLI's own version, a `terraform.tfvars` with your answers, and a `.gitignore` for the state and plan, which hold the generated secrets (keep the state in an encrypted remote backend). Terraform is never applied for you: run `terraform init`, `terraform plan` and review it before `terraform apply`. Each release also attaches `storyshelf-terraform-<version>.tar.gz` for installs that cannot fetch from GitHub.

### Inputs

| Name                                     | Default                  | Meaning                                                                                                                  |
| ---------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `name`                                   | required                 | Name prefix, 2 to 20 characters                                                                                          |
| `project_id`                             | required                 | The GCP project                                                                                                          |
| `image_version`                          | required                 | Release version of the image (no `v`)                                                                                    |
| `region`                                 | `us-central1`            | Must match the provider's region                                                                                         |
| `image_repository`                       | `""`                     | A full registry path (your mirror). Empty creates the ghcr.io proxy                                                      |
| `public_base_url`                        | `""`                     | `SHELF_PUBLIC_BASE_URL`, for a domain you map yourself; empty means the service's `run.app` URL                          |
| `auth_email`                             | `admin@example.com`      | Local admin login email (`SHELF_ADMIN_EMAIL`)                                                                            |
| `network`, `subnetwork`                  | `""`                     | An existing VPC and subnet (self links). Empty creates them                                                              |
| `cpu`, `memory`                          | `2`, `4Gi`               | Capture renders in the container, so do not go much lower                                                                |
| `min_instances`, `max_instances`         | `1`, `1`                 | Identical copies. At least 1 (validated). See [Running several instances](/guides/deployment/#running-several-instances) |
| `database_pool_size`                     | `10`                     | Connections per copy. `max_instances` × this must fit the database's limit                                               |
| `shutdown_grace_seconds`                 | `8`                      | Sets `SHELF_SHUTDOWN_GRACE_SECONDS`, 1 to 9 (see [Shutdown](#shutdown))                                                  |
| `existing_database_url_secret_id`        | `""`                     | A Postgres URL in Secret Manager. No database is created                                                                 |
| `database_tier`, `database_disk_size_gb` | `db-custom-1-3840`, `10` | Created database only                                                                                                    |
| `deletion_protection`                    | `true`                   | Protects the database and service. `false` also empties the bucket on destroy                                            |
| `labels`                                 | `{}`                     | Added to every resource that supports them                                                                               |

### Outputs

| Output                                                                       | Meaning                                        |
| ---------------------------------------------------------------------------- | ---------------------------------------------- |
| `url`                                                                        | The Cloud Run service URL                      |
| `service_name`, `service_account_email`                                      | The service and the identity it runs as        |
| `gcs_bucket`                                                                 | The Storybook bucket                           |
| `db_instance`, `db_private_ip`                                               | The Cloud SQL instance and its private address |
| `database_url_secret_id`, `admin_token_secret_id`, `auth_password_secret_id` | Secret Manager ids (references), never values  |
| `service_account_roles`                                                      | The exact grants (next section)                |

## Permissions

The service runs as its own service account, `service_account_email`, with exactly these grants (output `service_account_roles`). Nothing is granted at project level:

| Resource                                                                                                         | Role                                 |
| ---------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| The Storybook bucket                                                                                             | `roles/storage.objectUser`           |
| Each app secret (`SHELF_SECRET`, `SHELF_ADMIN_PASSWORD`, `SHELF_ADMIN_TOKEN`, the database URL, any git secrets) | `roles/secretmanager.secretAccessor` |

Cloud Run writes the container's logs itself, and the database is reached over its private IP with a password from Secret Manager, so no logging or Cloud SQL role is needed. Anyone can reach the service (`allUsers` has `roles/run.invoker`), so the app's sign-in is its only gate: the module generates `SHELF_ADMIN_PASSWORD`, and the image refuses to boot without it. The identity running Terraform needs enough rights to enable the APIs the module uses (`run`, `storage`, `secretmanager`, `artifactregistry`, and `sqladmin`, `servicenetworking`, `compute` for the database), which stay on at destroy.

Review these with your platform team before the first apply. They are also what you copy if you [adapt it to your own platform](#adapt-it-to-your-own-platform).

## Database and secrets

- **Private database.** Cloud SQL has no public IP, takes a private address from a reserved range through private services access, and requires TLS. The instance uses a CAS-issued server certificate, which names its private IP; the module's URL says `?sslmode=verify-full` and passes the instance's CA as `SHELF_DATABASE_CA`, so the app verifies the certificate. No live run has confirmed this yet. With your own database URL, see [Verify the database certificate](/guides/deployment/cloud/#verify-the-database-certificate).
- **Secrets.** `SHELF_SECRET`, `SHELF_ADMIN_PASSWORD`, `SHELF_ADMIN_TOKEN` and the database password are generated, and reach Cloud Run as Secret Manager references. Their values are also in the Terraform state, so keep the state in an encrypted backend with restricted access. Sign in as `admin@example.com` (or `auth_email`) with the password from `gcloud secrets versions access latest --secret "$(terraform output -raw auth_password_secret_id)"`; the break-glass admin token is `admin_token_secret_id`.
- **Existing database.** Put a `postgres://` URL in a secret and pass its id as `existing_database_url_secret_id`. The module creates no database or private services range. Set `network` and `subnetwork` if the database is private; the network path is yours.

## Domain and TLS

The service has the `*.run.app` HTTPS origin. For your own domain, map it yourself (a load balancer or a Cloud Run domain mapping) and pass `public_base_url`. Without it the app uses the service's deterministic `run.app` URL, so session cookies are `Secure`.

## Keep one instance running and shutdown

Capture runs in the background, so the service sets `cpu_idle = false` (CPU stays allocated between requests) and requires `min_instances` of at least 1. Without them captures stall: see [Keep one instance running](/guides/deployment/#keep-one-instance-running).

### Shutdown

Cloud Run sends SIGTERM and stops the container 10 seconds later. That window is not configurable. The app drains running captures for `SHELF_SHUTDOWN_GRACE_SECONDS` (`shutdown_grace_seconds`, 1 to 8, default 8), then hands the rest back to the queue. The process exits when that bounded shutdown ends, so even the largest value leaves 2 seconds of margin. A copy killed anyway loses its lease: the job is retried unless that attempt was its last, in which case the job and its build fail and admins are alerted.

## Sizing and cost

For a small team (a few projects, a few builds a day) the defaults are the starting point: 2 vCPU and 4 GiB with CPU always allocated, one instance, and a `db-custom-1-3840` Cloud SQL instance with 10 GB. Rough monthly cost is **130 to 200 USD** (an estimate, November 2026, for `us-central1`: the always-on instance, the database, plus storage and egress). Treat that as an order of magnitude and check the Google Cloud pricing calculator for your region. A smaller shape (1 vCPU and 2 GiB) costs less but leaves little room for parallel captures. Capture is the largest variable cost: Chromium needs about 100 to 300 MB per open page. See [Sizing memory for capture](/guides/deployment/#sizing-memory-for-capture).

## Backups

- **Database.** Turn on Cloud SQL automated backups and point-in-time recovery for the created instance, or use your own policy for an existing database.
- **Storage.** The bucket is versioned, so an overwritten or deleted blob can be recovered.
- **Order and restore.** Back up the database first, then storage, and restore both together. See [Back up and restore](/guides/backup-restore/), and run `storyshelf server check-storage` after a restore.

## Adapt it to your own platform

If your team won't use the module, you need three things:

1. **The image.** `ghcr.io/guptasiddhant/storyshelf:<version>` (`amd64` and `arm64`). It listens on port 3000 and bundles Chromium. Use at least 2 vCPU and 4 GB for capture, CPU always allocated and one instance minimum; the `-hosting` variant has no browser, for hosting without capture.
2. **The environment.** This is what the module passes:

   | Variable                                     | Value                                                                                                                                                   |
   | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `SHELF_GCS_BUCKET`, `GOOGLE_CLOUD_PROJECT`   | The bucket and project. Credentials come from the service account (Application Default Credentials). Setting another storage backend too stops the boot |
   | `SHELF_PUBLIC_BASE_URL`, `SHELF_TRUST_PROXY` | The public `https://` origin, and `1` behind a proxy                                                                                                    |
   | `SHELF_SECRET`, `SHELF_ADMIN_TOKEN`          | At least 32 random characters, the same on every copy (secret references)                                                                               |
   | `DATABASE_URL`, `SHELF_DATABASE_POOL_MAX`    | A Postgres URL (the Cloud SQL private IP), and connections per copy                                                                                     |
   | `SHELF_SHUTDOWN_GRACE_SECONDS`               | Drain time on SIGTERM, below the platform's 10 second window                                                                                            |

3. **The permissions** in the section above, attached to the container's own identity. Never put cloud access keys in environment files.

Put a load balancer or ingress in front that terminates TLS and forwards the original host. Keep the database off the public internet.
