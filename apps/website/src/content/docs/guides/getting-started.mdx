StoryShelf is a self-hosted visual testing platform for Storybook. You run one server, point your CI at it, and review pixel diffs in the browser.

<Screenshot
  name="projects-list"
  alt="The projects overview: a card per project with its latest build and review backlog"
  caption="What you will end up with: a project per Storybook, and what still needs review."
/>

You need a Storybook with a `.storybook/main.*` file, and a machine to run the server on. Pick one way to start the server below (both end in the same place), then follow steps 2 to 4.

<Aside type="caution" title="Three values you must set">
  The server starts with sign-in on and refuses to start without these.

  - `SHELF_SECRET`: at least 32 random characters. Generate it once and keep it; the data volume needs the same value on every start.
  - `SHELF_PUBLIC_BASE_URL`: the address people open in a browser, for example `http://localhost:3000`.
  - `SHELF_ADMIN_PASSWORD`: the first admin's password, at least 12 characters.
</Aside>

## 1. Start the server

<Tabs syncKey="server">
  <TabItem label="Docker">
    One command, with Chromium for capture, SQLite and local storage on a volume. Needs Docker.

    ```sh
    export SHELF_SECRET="$(openssl rand -hex 32)"
    export SHELF_PUBLIC_BASE_URL=http://localhost:3000
    # Choose a private admin password (12 or more characters); it is not echoed.
    printf 'Admin password: '; stty -echo; read -r SHELF_ADMIN_PASSWORD; stty echo; echo
    export SHELF_ADMIN_PASSWORD
    docker run -p 127.0.0.1:3000:3000 -v storyshelf:/data \
      -e SHELF_SECRET -e SHELF_PUBLIC_BASE_URL -e SHELF_ADMIN_PASSWORD \
      ghcr.io/guptasiddhant/storyshelf
    ```

    The server listens on `http://localhost:3000`. Keep `SHELF_SECRET`: the same `storyshelf` volume needs it on every start.

  </TabItem>
  <TabItem label="npm">
    Scaffold a server project and run it with Node.js 24 or later:

    <PackageManagers type="create" pkg="storyshelf" />

    Accept the defaults (SQLite, local filesystem, **Local accounts**). It writes the server, a `.env.example`, a README and Docker files, then prints the next steps:

    ```sh
    cd my-storyshelf
    export SHELF_SECRET="$(openssl rand -hex 32)"
    export SHELF_PUBLIC_BASE_URL=http://localhost:3000
    # Choose a private admin password (12 or more characters); it is not echoed.
    printf 'Admin password: '; stty -echo; read -r SHELF_ADMIN_PASSWORD; stty echo; echo
    export SHELF_ADMIN_PASSWORD
    npm install   # or pass --install to create-storyshelf
    npm start
    ```

    The server listens on `http://localhost:3000`. Instead of exporting the variables, copy `.env.example` to `.env`; the server reads it. A missing value stops the server with one line naming it.

    `create-storyshelf` needs a terminal; `--dir <path>` picks the output directory and `--install` installs the dependencies with the package manager that ran it.

  </TabItem>
</Tabs>

## 2. Sign in and create a project

Open `http://localhost:3000` and sign in as `admin@example.com` with your `SHELF_ADMIN_PASSWORD`. Choose **New project**, give it a name, and open it. A project with no builds shows **Get your first build**:

1. **Create a token.** It is shown once; copy it.
2. **Upload.** The card shows the command with your server URL and the project's slug filled in.

## 3. Upload a build

From your Storybook project, save the URL and slug once. This writes `.storybook/storyshelf.json`, which you commit (it holds no secret):

<PackageManagers
  type="dlx"
  pkg="storyshelf"
  args="init --url http://localhost:3000 --slug my-design-system"
/>

Then upload, with the token in the environment:

<PackageManagers type="dlx" pkg="storyshelf" args="" />

Set the token first: `SHELF_TOKEN=shelf_… npx storyshelf` (the card's `upload --url … --slug …` command is the same upload with the settings as flags). Bare `storyshelf` is `storyshelf upload`, and runs when `.storybook/storyshelf.json` exists. It builds your Storybook first when there is no `storybook-static` directory. StoryShelf renders every story on the server and diffs it against the branch baseline. The command prints each phase, then a summary and the link to the build:

```text
==> Creating build
--> Created build (0.1s)
==> Uploading Storybook
Uploading 26 of 32 files (the server has the rest)
--> Uploaded Storybook (0.1s)
Summary
  Files:    32
  Size:     4.8 MiB
  Stories:  full capture (24 stories)
  Build:    01M7YHNPPVYK1EGAKNAC3APM01
  Time:     5.3s
View the build: http://localhost:3000/projects/my-design-system/builds/01M7YHNPPVYK1EGAKNAC3APM01/diff
```

Add `--wait` to follow the build until it is captured; the exit code says how it ended (see [Gating CI with `--wait`](/guides/cli/client/#gating-ci-with---wait)).

<Aside type="tip">
  Keep the token in `SHELF_TOKEN` (a CI secret), never in `.storybook/storyshelf.json`: a `token` key there is refused. See [CI setup](/guides/ci/) for a pipeline.

On a server with sign-in off, `npx storyshelf create --url http://localhost:3000 --name "My Design System"` creates the project and a CI token and writes the config. With sign-in on, `create` needs the site admin token (`--token`, or `SHELF_ADMIN_TOKEN`) and refuses without it; the UI steps above need no token and are the way to start. With the admin token it creates the project only and points you to its page for the CI token, because a token made on the command line has no user behind it and could not upload.

</Aside>

## 4. Review

The first build has nothing to compare against, so it waits for review: open the build and approve it to make it the baseline. Upload again and the new build is compared with that baseline; an unchanged Storybook passes with nothing to review. A build that needs attention shows **N to review** on its project card; open it, and choose **Review diffs** for the review workspace: a filmstrip of changed stories, baseline, current and diff side by side (or swiped, blended or flipped), and **Approve** / **Reject** with the keyboard.

<Screenshot
  name="diff-review"
  alt="The review workspace: snapshot filmstrip, baseline | current | diff comparison, and the action bar"
  caption="The review workspace. Approving a change moves you straight to the next one."
/>

When every change is decided, the build's status check goes green and you can merge.
