`@storyshelf/db` holds every database adapter StoryShelf ships, one subpath each: `/sqlite`, `/postgres` and `/mysql`, plus a subpath per driver or cloud preset. Each driver is an optional peer that only its own subpath loads, so a SQLite server never installs a Postgres or MySQL client. All of them implement the same `DatabaseAdapter` contract, so the rest of the application does not change when you switch databases.

### Durability

The adapter runs SQLite in WAL mode with `synchronous = NORMAL`. A commit does not wait for the disk to flush, so writes are faster, and the trade-off is:

- **An application crash loses nothing.** Every committed transaction is in the write-ahead log.
- **An operating-system crash or power loss can lose the last committed transactions**, but never corrupts the database.

For a host that must keep every committed transaction through a power cut, opt out to a sync on every commit:

```ts
createSqliteDatabase("/var/lib/storyshelf/shelf.db", { synchronous: "full" });
```

The `better-sqlite3` and `bun:sqlite` presets take the same `synchronous` option. D1 and Turso manage durability themselves and are unaffected.

The former `@storyshelf/db-turso` package is retired — see `docs/deprecated.md` in the repo.

## When to use it

Use SQLite for a single-node deployment or local development, and pair it with [local storage](../core/) for the simplest self-hosted setup. Choose Postgres when you need a managed relational database or already run Postgres for your team; choose MySQL or MariaDB when that is what your team already runs or your platform provides. For multi-node deployments pair a server database with [S3-compatible storage](../storage/) when instances do not share a filesystem.
