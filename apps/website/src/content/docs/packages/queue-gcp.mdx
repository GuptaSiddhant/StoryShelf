`@storyshelf/queue-gcp` backs StoryShelf's capture queue with **Google Cloud Pub/Sub**. It implements the `CaptureQueue` / `PollableCaptureQueue` contract from `@storyshelf/core`: the server publishes a message per build, and a separately-assembled [worker](/packages/worker/) pulls from a subscription and runs the capture. Switching between in-process, Redis, SQS, Azure, and Pub/Sub is a single dependency swap, with no router or build changes.

## Register the queue

Pass the Pub/Sub queue as the `captureQueue` option of `createShelfApp`:

```ts
import { createShelfApp } from "@storyshelf/app";
import { createGcpPubSubQueue } from "@storyshelf/queue-gcp";

const queue = createGcpPubSubQueue({
  projectId: process.env.GOOGLE_CLOUD_PROJECT!,
  topic: "capture-jobs",
  subscription: "capture-jobs-worker",
});

const app = createShelfApp({
  database,
  storage,
  captureQueue: queue,
});
```

The server only publishes (`enqueue`). Workers use the same factory to pull, acknowledge, and requeue.

## Options

```ts
interface GcpPubSubQueueOptions {
  projectId: string;      // GCP project ID
  topic: string;          // topic short name
  subscription: string;   // pull subscription short name
  keyFilename?: string;   // service-account JSON key; omit to use Application Default Credentials
  apiEndpoint?: string;   // custom endpoint, e.g. the Pub/Sub emulator host
  publisher?: v1.PublisherClient;   // injected client (tests)
  subscriber?: v1.SubscriberClient; // injected client (tests)
  logger?: Logger;
}
```

Topic and subscription are **short names**; the adapter builds the full resource paths from `projectId`. Credentials come from Application Default Credentials (a Cloud Run service account, `GOOGLE_APPLICATION_CREDENTIALS`, or workstation login) unless you pass `keyFilename`.

## How messages flow

- **Enqueue** publishes `{ buildId, reqId, queuedAt, status, traceparent }` as JSON, with a `buildId` message attribute.
- **Poll** uses synchronous pull, one message at a time. It returns `null` straight away when the subscription is empty (no long-lived streaming state).
- **Ack** acknowledges the message. **Nack** resets the ack deadline: immediately, or after `delayMs` (rounded up to whole seconds). With `requeue: false` the message is acknowledged and dropped.
- **Attempts** come from the message's `deliveryAttempt`. Pub/Sub only fills this in when the subscription has a **dead-letter policy**, so configure one.
- **Malformed messages** (no `buildId`) are acknowledged and discarded with a warning.
- `status`, `active`, and `recent` return empty results: the `builds` table is the source of truth for remote queues, same as SQS and Redis.
- **Lifecycle:** `setup` checks the topic exists, `health` checks the subscription exists, and `teardown` closes only the clients the adapter created itself.

## Create the topic and subscription

Use a pull subscription with an ack deadline longer than your slowest capture and a dead-letter policy for poison messages. The GCP deploy target (`storyshelf server init`) writes this as Terraform:

```hcl
resource "google_pubsub_subscription" "capture" {
  name  = "capture-jobs"
  topic = google_pubsub_topic.capture.id

  ack_deadline_seconds       = 300
  message_retention_duration = "604800s"

  dead_letter_policy {
    dead_letter_topic     = google_pubsub_topic.capture_dlq.id
    max_delivery_attempts = 5
  }
}
```

Make the `subscription` option match the subscription you actually created. Grant the server's service account `roles/pubsub.publisher` and the worker's `roles/pubsub.subscriber`. Terraform creates the resources, but IAM bindings stay with your org policy. Pub/Sub also needs permission to publish to the dead-letter topic and to acknowledge from the subscription; see Google's dead-letter docs.

## Run a worker

```ts
import { createGcpPubSubQueue } from "@storyshelf/queue-gcp";
import { createCaptureWorker } from "@storyshelf/worker";
import { createPostgresDatabase } from "@storyshelf/db-postgres";
import { createGcsStorage } from "@storyshelf/storage-gcs";
import { createPlaywrightCaptureRunner } from "@storyshelf/runner-playwright";

const worker = createCaptureWorker({
  queue: createGcpPubSubQueue({
    projectId: process.env.GOOGLE_CLOUD_PROJECT!,
    topic: "capture-jobs",
    subscription: "capture-jobs-worker",
  }),
  db: createPostgresDatabase({ url: process.env.DATABASE_URL! }),
  storage: createGcsStorage({ bucket: process.env.GCS_BUCKET! }),
  runner: createPlaywrightCaptureRunner(),
  scratchDir: "/tmp/shelf",
});
await worker.start();
```

`storyshelf server init` / `storyshelf worker init` scaffold the same composition when **Pub/Sub** is chosen for the queue. For scaling, retries, shutdown, and monitoring, see [Remote capture workers](/guides/deployment/remote-workers/#gcp-pubsub).

## Local development

Point `apiEndpoint` at the [Pub/Sub emulator](https://cloud.google.com/pubsub/docs/emulator) and create the topic and subscription there first. The adapter's live test suite runs against real Pub/Sub, not the emulator.

## When to use it

Use `queue-gcp` on Google Cloud (Cloud Run, GKE) where the server and capture worker should be decoupled. For single-host deploys, `InMemoryCaptureQueue` is sufficient. For other platforms see [queue-sqs](/packages/queue-sqs/), [queue-azure](/packages/queue-azure/), and [queue-redis](/packages/queue-redis/).
