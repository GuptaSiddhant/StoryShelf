# Design sources and build labels

> Part of the [StoryShelf architecture spec](./README.md).

## Design Sources

Design links attach to a **component (story file)**, never to a single state or to a build label. A state's design button appears iff its file resolves a link; there is no project-default or label fallback on snapshots. The vendor specifics live behind the **`DesignProvider` adapter** (ADR 0018, `@storyshelf/core/adapter/design`); core owns everything else. Servers opt in with `design: [createFigmaDesign()]` (`@storyshelf/design-figma`); with no provider wired, no design links are extracted or shown.

- **Provider contract:** `parseUrl(raw) → DesignRef | null` (`{fileKey, nodeId, url}`), `create({credential}) → DesignClient` with `fetchMetas(fileKey, refs)` and `fetchRenders(fileKey, nodeIds)` (batched per file; API failures map to a `DesignState` per ref instead of throwing). Metadata (`credentialLabel`, `credentialHelp`, `urlHint`, `credentialMaxAgeDays`) drives the Design settings copy. The capture consumer in the app uses the same list, so declared links are validated during capture.
- **Story parameters:** `parameters.storyshelf.figma` (plain URL string) wins over the Storybook `design` addon shape (`string | {url} | {type,url} | {type,url}[]`, first URL wins). `extractDesignUrl()` runs at discovery with the configured providers' parser and stores the result on `StoryEntry.designUrl` → `snapshots.design_url`, keeping `StoryParameters` capture-clean. Links no provider accepts are dropped and logged; capture never fails.
- **Resolution (read time, per file):** manual mapping (`design_links` by normalized `import_path`) > story parameters. States of one file are deduped; if they disagree the distinct set is shown rather than guessing. Keying by `import_path` survives new builds, not file renames: after a story file is renamed or moved, update its mapping (the component page shows where it moved).
- **Design settings tab:** project file links (library header), the manual component-mapping table, and one credential card per configured provider (admin-only, write-only, encrypted, rotated via `previousSecret`). The tab shows days left against the provider's maximum credential age and the last health (`ok` / `unauthorized` / `forbidden`). Without a provider the tab explains how to configure one.
- **Metadata cache:** with a credential, the review page and library refresh `design_nodes` rows older than 15 minutes through the provider client (Figma: the shared `httpJson` helper with `X-Figma-Token`). Links of one file share one metadata call and one render call; files refresh three at a time and at most ten links per library view. The whole refresh runs under a ~1.5 s page budget that aborts the provider calls (what landed stays cached for next time). A design edited after the snapshot's `baseline_version` shows a non-blocking stale banner; a missing node/file shows a deleted notice; API outages degrade to plain deep links. None of this touches the `409 baseline_changed` guard.
- **Render cache:** for node links the provider's render is downloaded at fetch time (signed vendor URLs expire, so they are never hot-linked) into storage at `{projectId}/design/{provider}/{fileKey}/{node}.png` and re-fetched only when the file `version` moves (`render_version`). `GET /api/v1/projects/:slug/design/renders/:renderId` (the internal `design_nodes` row id, not a provider node id) serves it to viewers; a request whose `?v=` matches the stored version is cached `immutable`. A render failure keeps the previous render and the metadata. A **deleted** node drops its render (row and stored PNG), so a design that no longer exists is never shown as reference; an auth failure (`unauthorized`/`forbidden`) keeps the last good name, version and render and only flips the state.
- **Render lifecycle:** one PNG per linked node, overwritten in place when the file version moves, so storage is bounded by the number of distinct linked nodes. Renders are not evicted by build purge (they are not build artifacts); a link removed from settings (or a deleted project) leaves its PNG behind — small, bounded, and safe to delete by hand under `{projectId}/design/`.
- **Surfaces:** the review page shows a reference pane under the diff stage (reference only — never diffed); library cards open a click popover with the cached render and `Open in <provider>`. Whole-file links have no render and stay deep links.
- **Member connections (ADR 0011):** when the project has no credential and the operator configured OAuth for the provider (`createFigmaDesign({ oauth })`), signed-in members see a "Connect <provider>" prompt. Their tokens live in `user_connections`; entries fetched with them carry `design_nodes.viewer_id = user` and (with their renders under `.../user-<id>/...`) are served only to that user. The project credential always wins, and a member token is used only during that member's own visits.
- **Non-goals:** pixel-diffing against design renders, token mapping, build-level `figma` labels.

## Build Labels

Builds carry **labels** — typed values that identify related builds and link out to external systems. Labels drive search and stable, refreshable URLs: a manager can bookmark a Jira issue; a dev can refresh a PR/MR label to always see the latest build.

- **Types are project-defined** (`label_types`). Each project configures the kinds it uses — a GitHub team defines `pr`, a GitLab team `mr`, and either adds `jira`, `linear`, `figma`, `custom`. A type has a `key`, a display `name`, an optional `color`, and a **`link_template`** that turns a value into an external URL (`{repo}` and `{branch}` resolve from the build):
  - `pr` → `https://github.com/{repo}/pull/{value}`
  - `mr` → `https://gitlab.com/{repo}/-/merge_requests/{value}`
  - `jira` → `https://myorg.atlassian.net/browse/{value}`
  - `linear` → `https://linear.app/myorg/issue/{value}`
  - `figma` → `https://www.figma.com/file/{value}`
    The review page renders label values as clickable links.
- **Attached at upload time.** The CLI attaches labels via `--label key=value` (repeatable), and always attaches `branch=<git_branch>` (a seeded label type). CI templates populate `pr` (GitHub) or `mr` (GitLab) automatically, and `jira`/`linear`/`figma` from explicit flags or branch/commit-message patterns. Unknown keys are auto-created as `custom` type.
- **Persistent builds.** `persistent` is a built-in, **non-removable** label type: a build bearing it is never purged. The CLI detects git tags on the uploaded commit (`git tag --points-at <sha>`) and attaches one `persistent` label per tag (value = tag name, e.g. `v1.2.3`), so release/tag builds survive retention automatically.
- **Search:** `GET /builds?label=pr:123`.
- **URL-safe values.** Label values (branch names, git tags) may contain slashes and special characters. In URLs, values are encoded with `encodeURI` and the value route segment is a wildcard that captures slashes, so `branch=feature/foo` round-trips as `…/labels/branch/feature/foo`. Values are deliberately **not** slugified — slugifying would collide (`feature/foo` vs `feature-foo`).
- **Label page:** `GET /projects/:slug/labels/:key/:value` lists every build bearing that label (latest first) with the external link — a bookmarkable "latest build for this PR/issue" page. Resolved by an indexed query over `build_labels` joined to `builds` (no denormalised pointer to keep in sync).
