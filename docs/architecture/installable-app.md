# Installable app, offline Storybooks and web push

> Part of the [StoryShelf architecture spec](./README.md). Decisions: [ADR 0048](../adr/0048-installable-app-offline-push.md).

The app has one piece of client-side state: a service worker with device storage. Everything else stays server-rendered. Status is per item: **landed** is in the code, **planned** is written from the ADR and names the task (epic #837) that makes it true. Update each marker when its task merges.

## Manifest (landed, #838)

`GET /manifest.webmanifest` (`app/src/routers/manifest.ts`, class `hosting`, no session, `Cache-Control: no-cache`). Name and `short_name` come from the configured product name, `start_url` and `scope` are `/`, `display` is `standalone`, theme and background colours are the light theme's base surface, and the icons are 192, 512 and maskable 512. The document head links it and sets `theme-color` (`shell/document.tsx`).

## The service worker (landed #839; jobs planned)

`GET /sw.js` (`app/src/routers/service-worker.ts`, class `hosting`, no session, `Cache-Control: no-cache`). The script is generated by `shell/service-worker.ts`; `shell/boot-script.ts` registers it with scope `/`. The app never sends `Service-Worker-Allowed`, so a published Storybook's own worker controls only its build path.

Three jobs only:

| Job                               | Status                                                |
| --------------------------------- | ----------------------------------------------------- |
| Serve opted-in Storybooks offline | planned (#841)                                        |
| Show the offline home page        | planned (#842, rendered by the worker from IndexedDB) |
| Show push notifications           | planned (#845: `push` and `notificationclick`)        |

Today every request goes to the network, and a failed navigation shows an inline "You are offline" page (503, `no-store`). Limits that hold for every job: the worker never caches app HTML, `/api/v1` answers, session state or CSRF tokens; a navigation outside `/offline` that fails falls back to the offline home page, never a stale app page; `notificationclick` opens only paths on the app's own origin.

`POST /auth/logout` sets `Clear-Site-Data: "cache", "storage"` (landed, #839), which clears Cache Storage and IndexedDB and unregisters the worker. Planned (#845): the page first unsubscribes the device's push endpoint.

## Offline sync (endpoint landed #840; engine planned)

`GET /api/v1/offline?projects=<slug,...>` (`app/src/routers/offline.ts`, `offline.handlers.ts`; class `hosting`; `Cache-Control: private, no-store`). At most 100 slugs. For each slug the caller may read it answers `{ slug, name, buildId, commit, entries: [{ path, hash, size }], maxOfflineDays }`:

- The build is `BuildModel.latestApprovedDefault`, the one `/projects/:slug/storybook` opens.
- Access is `publishedAccess`, the check every published-file route uses. An unknown slug, a hidden project and a project with no published manifest are all left out, so the answer never says which exist.
- `entries` come from the build's manifest (`loadManifest`); a blob's size is measured from storage once and kept in memory by hash.
- `maxOfflineDays` is `config.offline.maxOfflineDays` (1–365, default 30; `maxOfflineDaysOf` in core).

Device state (planned, #841; IndexedDB, never on the server): the chosen projects, the storage cap (default 500 MB, set on the offline page), the path → hash map per project and the last successful sync time. Files are stored in Cache Storage under their content hash; a sync downloads only missing hashes, deletes projects missing from the answer, and then deletes hashes no kept project uses. It runs on every app start while online and through periodic background sync where offered. The app asks for persistent storage; a project that would pass the cap is refused with its size, and nothing is evicted silently.

Serving (planned, #841 and #842): offline copies are answered from the cache at `/offline/<slug>/…`, never at the published paths; `/offline` is the home page, one link per kept project with the commit and last sync time. The worker stops serving a project `maxOfflineDays` after its last successful sync. It never copies a sandbox header from published files (ADR 0048, amendment 2026-11-11).

Hosting modes (ADR 0048 amendment): offline Storybooks need `trusted` mode. Planned (#841): the sync endpoint and the opt-in UI report the other modes and nothing is cached; the landed endpoint does not check the mode yet. In `trusted` mode uploaded code runs on the app origin and can read or poison its Cache Storage and IndexedDB, so the cache is not a boundary between projects.

Not offline: app pages, review, comments, other branches, older builds and signed `/_s/` URLs.

## Web push (all planned)

- **Table (#843).** `push_subscriptions`: `id`, `user_id`, `endpoint` (unique), `p256dh`, `auth`, `label`, `created_at`, `last_success_at`, `failure_count`, in all three dialects and the core row type. Add it to [`data-model-access-and-system.md`](./data-model-access-and-system.md) when it lands.
- **Notifier (#844).** `integrations/push/` in core (ADR 0049): a `message` notifier with `audience: "person"`. Web Push with node's own crypto: VAPID (RFC 8292) and `aes128gcm` (RFC 8291), tested against the RFC vectors; no new dependency. Requests go through core's HTTP utilities and URLs are logged only as `redactUrlForLog`.
- **Keys (#845).** The VAPID key pair and contact `subject` are server configuration from the environment. The private key never appears in logs, errors, API output or the database; only the public key is served, at `GET /api/v1/push/public-key`. Without keys push is off, its routes answer 404 and the UI hides it.
- **Devices (#845).** `POST /api/v1/me/push-subscriptions` and `DELETE /api/v1/me/push-subscriptions/:id` (class `hosting`, signed-in user). A 404 or 410 from the push service deletes the row.
- **Delivery (#845).** `push` is a `via` kind on the personal notification subscription, off until enabled on a device, following the user's event preferences. One job per recipient on the `notify` queue (ADR 0040). The payload is a title, a one-line body and a relative path from the `UrlBuilder`; nothing is sent without a confirmed public origin (`notificationOrigin`).
- **UI (#846).** The push settings page.

Every route above is class `hosting`, so offline Storybooks and push work on a hosting-only deployment; none depends on `testing`.
